大家好，我是二哥呀。

看到美团员工这样一则爆料。

![](https://cdn.paicoding.com/stutymore/sucai-20260827110022.png)

LongCat，美团自研的大模型家族。LongCat-2.0 有 1.6 万亿参数，MoE 架构，每次推理激活 480 亿参数，用国产芯片（华为昇腾、摩尔线程、沐曦）训练出来的，MIT 协议开源。

【截图：LongCat-2.0 参数概览；风格：data-board；截图目标：展示 LongCat 的模型规模和技术路线；关键词：1.6万亿参数、MoE、国产芯片】

一家做外卖起家的公司，做出了参数量比肩前沿模型的开源大模型。我第一次看到这个消息的时候愣了一下——不是不信，是觉得美团的决心比我想象中大得多。

美团做大模型的逻辑其实很清楚。外卖推荐、商家运营、骑手调度、客服对话、到店团购——每一个都是典型的 Agent 场景。用户说一句话，系统替你把事情办了。这种场景不需要模型写小说、做推理竞赛，需要的是模型能准确理解意图、稳定调用工具、可靠地完成任务。LongCat 就是这些场景背后的基座，C 端的小团、小美，B 端的 NoCode 低代码平台，都跑在 LongCat 上面。

所以这位员工说「资源一路绿灯」，我是信的。做基座的团队，公司所有业务线都是你的客户，你的产出直接体现在核心产品里。晋升答辩的时候，别人讲的是「优化了某个模块的性能」，你讲的是「支撑了公司整个 AI 战略的落地」。叙事量级不一样，评委的感受自然也不一样。

但我想聊的不是「怎么挤进明星团队」。

大厂里这样的王牌项目，一个公司也就那么几个，名额有限，不是想进就能进的。我更想聊的是这条爆料背后的另一个信号——Agent 方向在大厂里的战略地位，已经和两年前完全不一样了。

两年前说「做 AI」，大部分人想到的是算法岗——训模型、调参数、写 CUDA 内核。门槛确实高，普通工程师很难够到。

Agent 方向要的是工程能力。能把模型的输出包装成可用的产品，能管好上下文、调好工具、处理好异常、评估好效果。

这些能力，后端工程师天然就有基础。RAG 的本质是检索工程，上下文压缩的本质是状态管理，工具调用的本质是 API 编排，Harness 的设计思路和微服务架构有相通的地方。做过后端的人去学 Agent，会发现很多概念似曾相识，只是换了个场景在用。

今年美团、阿里、腾讯、字节招 Agent 方向的岗位比去年多了很多。不只是模型公司在招，传统互联网大厂也在大量招——它们有场景、有数据、有业务需求，缺的是能把 Agent 做出来、做稳定的工程师。

今天这篇面试题，14 道，从 RAG 的切块、检索一路聊到 Agent 和 Harness 的区别，再到 Prompt Cache 和 Vibe Coding。写答案之前，我把派聪明（RAG 知识库项目）和 PaiCLI（终端 Agent 项目）的源码重新翻了一遍，每道题的答案都能落到具体实现上。

如果你是一位愿意相信努力、相信过程、相信一步一个脚印、相信自己能在 AI 时代分一杯羹的人，那接下来的硬核内容，希望你能认真读一读。

## content

### 01、你当时为什么会想到做这个智能运维 Agent 项目？

“运维场景的痛点太明显了。一个线上告警进来，工程师要登录好几个系统——先看监控面板，再翻日志，再查配置变更记录，再对照运维文档。一套流程走下来差不多要半个小时，大部分时间花在信息收集上，真正做判断的时间反而很短。”

【截图：运维排查流程对比；风格：swimlane；截图目标：对比人工排查和 Agent 辅助排查的流程差异；关键词：告警、日志、运维文档、Agent】

“Agent 能把信息收集这个环节自动化。接到告警后自动检索相关的运维文档和历史 case，调用工具查日志、拉指标，把相关信息汇总好，给出初步判断。工程师只需要确认和执行就行了。”

“技术上，用 RAG 检索运维知识库里的文档，用 ReAct 循环驱动 Agent 的推理和工具调用。整个项目的核心挑战其实不在 Agent 本身，在 RAG 这一环——后面好几道题都在问这个。”

### 02、系统运转流程是怎样构思的，技术选型的依据是什么？

“整体分五步。”

【截图：智能运维 Agent 系统架构；风格：swimlane；截图目标：展示从用户输入到结果输出的完整流程；关键词：意图理解、RAG检索、ReAct推理、工具调用】

“用户输入告警描述或运维问题，Agent 先做意图理解，判断是要查文档还是要执行操作。然后调 RAG 检索相关的运维文档，把检索结果注入上下文。Agent 结合检索结果做推理分析，需要更多信息就继续调工具查日志、拉监控指标，最终输出排查建议或直接执行操作。”

“选型有几个考虑。Spring AI 是因为公司后端技术栈是 Java，团队熟悉。ES 是因为它同时支持向量检索和全文检索，一个组件搞定混合检索，不需要再引入专门的向量数据库。Embedding 用的是阿里 DashScope 的 text-embedding-v4，2048 维，中文效果不错。推理模型用 DeepSeek 和 Qwen，性价比高。”

【截图：技术选型对照表；风格：data-board；截图目标：列出每个组件的选型理由；关键词：Spring AI、ES、DashScope、DeepSeek】

“没选 LangChain 那套 Python 生态，原因很简单——和公司现有的 Java 基础设施对接方便，部署运维不需要额外维护一个 Python 服务。”

### 03、为什么使用 RAG？模型上下文窗口已经很大了，为什么不直接把文档都交给 Agent？

“上下文窗口大不意味着应该把所有文档都塞进去，三个原因。”

“第一个是成本。运维知识库有几百篇文档，每次请求全量送进去，token 消耗太大了。RAG 按需检索，每次只取最相关的几个片段，成本可控。”

【截图：全量输入 vs RAG 检索成本对比；风格：data-board；截图目标：对比两种方式的 token 消耗差异；关键词：token成本、按需检索、全量输入】

“第二个是准确率。研究表明模型处理长上下文时，对中间部分的信息容易遗漏——就是所谓的「Lost in the Middle」现象。文档越多，相关信息被淹没在无关内容里的概率越大。”

“第三个是实时性。文档更新之后，RAG 只需要更新索引，不需要每次都重新组装输入。全量塞入的方式，文档一变就得改输入流程。”

“RAG 还有一个好处是可溯源——每条检索结果带着文件名、页码、匹配分数，回答里的每个论点都能追溯到原始文档，方便工程师验证。”

### 04、RAG 和让 Agent 通过 grep 自行检索，不考虑 token 时各有什么优劣？

“这两种方式适用的场景不一样。”

“RAG 的优势是语义理解。用户搜「内存不够了」，RAG 能召回「OOM 问题排查指南」「Java 堆空间溢出处理」这些文档，因为向量嵌入捕捉了语义上的相关性。但 RAG 需要一套预处理管线——切块、嵌入、索引，文档格式变了或者嵌入模型换了，整套管线都得重新跑。”

【截图：RAG vs Agent grep 对比；风格：data-board；截图目标：对比两种检索方式的优缺点；关键词：语义检索、精确匹配、预处理】

“Agent grep 的优势是精确匹配和零预处理。搜一个错误码、一个配置项、一个函数名，grep 直接精确命中，不需要提前做索引。而且文件改了，grep 搜的就是最新内容，没有索引更新的延迟。但 grep 没有语义理解能力——搜「内存不够了」找不到「OOM」，因为字面上没有交集。”

“Claude Code 就是用 ripgrep 做代码搜索的，不用 RAG。因为代码是精确的，函数名就是函数名，grep 加正则表达式就够了。Agent 可以根据第一轮搜索结果调整关键词，迭代几轮就能找到目标。”

“但运维文档是自然语言写的，同一件事有很多种说法。这种场景下 RAG 的语义匹配明显占优。我的做法是知识库用 RAG，代码仓库用 grep，按内容类型选方案。”

### 05、RAG 中间哪些步骤对你构成了挑战，并会影响最终效果？

“挑战最大的是切块和检索排序。”

“切块的难度在于粒度。块太大，一个 chunk 里混着多个主题，检索到了但噪音多，模型生成的回答容易跑偏。块太小，上下文被切断了，模型看到一段话不知道在说什么。”

【截图：切块粒度权衡；风格：data-board；截图目标：展示块大小对检索质量的影响；关键词：chunk大小、噪音、上下文完整】

“我们最终用的是 512 字符一个块、100 字符重叠。这个值是试出来的，不是算出来的。512 在运维文档里差不多是两三个自然段，刚好能覆盖一个完整的操作步骤或故障描述。”

“检索排序的难度在于权重配比。BM25 和向量得分的量纲不一样，直接加权没有意义，得归一化之后再配比。我们目前 KNN 权重 0.2、BM25 权重 1.0，关键词匹配的权重明显更高——因为运维文档里有大量专有名词和错误码，精确匹配比语义匹配更重要。”

### 06、如果你的 Markdown 文件没有标题，要怎么切分？

“三级降级。先按双换行切段落，一个段落就是一个候选块。段落太长了，再按句号、问号、感叹号这些句子边界切分。切完之后检查短块——两个相邻的短块加起来没超过上限，就合到一起，避免产生太碎的片段。”

【截图：无标题文档切分策略；风格：three-layer；截图目标：展示段落→句子→合并三级降级流程；关键词：段落切分、句子切分、短块合并】

“我们的最小块设了 100 字符，低于 100 的自动往前合并。”

“还有一个做法是父子文档。父 chunk 用大窗口，差不多一整个章节的大小。子 chunk 做细粒度切分。检索的时候用子 chunk 做匹配，命中之后把对应的父 chunk 送给模型，保证上下文完整。两层都存在 ES 里，通过 chunk ID 关联。”

### 07、混合检索中，关键词检索和向量检索各有什么缺点？

“关键词检索（BM25）的缺点是没有语义理解。它只做词频统计和精确匹配。搜「内存不够了」，包含「OOM」「OutOfMemoryError」的文档一条都召不回来，因为字面上没有交集。同义词、缩写、中英文混用，BM25 全都处理不了。”

【截图：BM25 vs 向量检索盲区对比；风格：data-board；截图目标：对比两种检索方式的盲区；关键词：BM25精确匹配、向量语义理解、互补】

“向量检索的缺点是对精确关键词不敏感。用户搜一个错误码「ERR_10042」，向量检索有时候会把一篇泛泛谈错误处理的文档排在前面，因为在向量空间里这两个内容的距离差不多。运维场景下这个问题尤其严重——错误码、配置项、IP 地址这些精确信息，向量检索经常搞混。”

“混合检索就是让两个互补。我们的做法是先用向量 KNN 召回一个大候选集，再在候选集上跑 BM25 重排序，让精确匹配好的结果排到前面。”

### 08、短 query 与长 chunk 向量化后怎么比较？

“这个问题在向量检索里确实存在。chunk 可能有一两百个字，嵌入之后向量的信息密度高、语义方向明确。query 只有三五个字，嵌入之后向量信息密度低、方向模糊。两个向量做相似度计算，短的那一方天然吃亏——它的方向不够'具体'，和很多 chunk 的相似度都差不多，区分度不高。”

【截图：短 query vs 长 chunk 向量空间示意；风格：whiteboard；截图目标：可视化短文本和长文本在向量空间中的分布差异；关键词：信息密度、向量方向、区分度】

“解决方案有两个方向。一是查询扩展，把短 query 补充成更完整的表述。比如用户输入「OOM」，扩展成「Java 应用 OutOfMemoryError 内存溢出排查方法」，补齐语义上下文。”

“二是 HyDE（Hypothetical Document Embeddings，假设性文档嵌入）。先让 LLM 根据 query 生成一段假设性的回答文本，用这段文本的向量去检索。假设性文本的长度和知识库 chunk 接近，信息密度对齐了，检索效果比直接用短 query 好不少。”

#### 你有没有对比过长 query 和短 query 在向量召回上的差异？

“对比过。三五个字的 query 召回精度确实差不少。只有一个关键词的时候，向量方向太泛了，召回的前 5 条里可能只有 1 条是真正相关的。换成一句完整的话，相关率能到 3 到 4 条。”

【截图：短 query vs 长 query 召回对比；风格：data-board；截图目标：展示不同 query 长度下的召回精度差异；关键词：短query、长query、召回精度】

“这也是我们把 BM25 权重设得比向量高的原因之一——运维场景下用户经常就丢一个错误码过来，三五个字，BM25 反而比向量检索靠谱。”

### 09、除了压缩以外，对长 query 还会做什么处理？

“长 query 的问题不只是太长。”

“第一个处理是意图分解。用户写了一大段，里面可能混着两三个问题。拆成多个子查询分别检索，每条 query 只对应一个意图，召回精度比一条混合 query 高得多。”

【截图：长 query 处理流程；风格：swimlane；截图目标：展示意图分解→关键词提取→去噪的处理流程；关键词：意图分解、关键词提取、去噪】

“第二个是关键词提取。从长文本中提取核心实体和术语，用这些关键词做精确匹配补充语义检索。”

“第三个是去噪。用户输入里经常有礼貌用语、重复表达、无关的背景描述。这些在检索前要去掉，否则会稀释 query 向量的语义方向。”

### 10、剩余 1% 到 2% 的错误怎样识别？

“三道防线。”

“第一道是 LLM-as-Judge（模型裁判）。定义一组评分标准——回答和引用内容是否一致、有没有幻觉、有没有遗漏关键信息——让模型自己打分。好处是成本低、速度快，能覆盖大批量样本。”

“第二道是人工校准。定期随机抽一批模型评过分的样本，人工复审，算一致率。一致率低了说明评分标准漂移了，要调整。两道缺一不可——只用模型裁判，评测体系自己漂移了都不知道。”

【截图：三道错误检测防线；风格：three-layer；截图目标：展示 LLM-as-Judge → 人工校准 → 置信度阈值三层机制；关键词：模型裁判、人工校准、置信度】

“第三道是置信度阈值兜底。模型输出时能拿到 token 级别的概率分布，整体置信度低于阈值的回答标记为「不确定」，提示用户人工确认。”

#### 有没有考虑给产出增加检测机制？

“考虑过引用核验。让模型输出的时候标注引用来源，然后用另一个 LLM 检查引用的原文是否真的支持这个结论。”

【截图：引用核验流程；风格：swimlane；截图目标：展示引用核验如何检测幻觉；关键词：引用来源、NLI、蕴含判断】

“原理类似 NLI（Natural Language Inference，自然语言推断）。把模型的结论和引用原文做蕴含关系判断：支持、矛盾、无关。矛盾或无关的就是幻觉，直接标出来。”

### 11、Agent 和 Harness 分别是什么？有什么区别？

“Agent 就是一个能自主决策的执行循环。就是 LLM 加工具。LLM 负责理解问题、制定计划、做判断，工具负责执行具体操作——查数据库、调 API、读文件。两者组合起来形成「观察 → 思考 → 行动」的循环，这个循环就是 Agent。”

【截图：Agent 核心循环；风格：whiteboard；截图目标：展示观察→思考→行动的 ReAct 循环；关键词：LLM、工具调用、ReAct循环】

“Harness 是 Agent 外面的工程设施。Agent 管的是「做什么决策」，Harness 管的是「在什么条件下做决策」。Prompt 怎么组装、上下文怎么管理、工具怎么注册、权限怎么控制、日志怎么记录——这些都是 Harness 的职责。”

“Claude Code、Codex、Qoder，底层用的模型可能差不多，但产品体验差距很大。差的就是 Harness 这一层。同样一个 LLM，好的 Harness 能让它稳定输出高质量结果，差的 Harness 让它经常偏离预期。”

#### Harness 做了哪些事情，能让 Agent 更好地执行任务？

“具体来说有这么几件事。”

“Prompt 组装——把系统指令、用户输入、工具结果、对话历史按层级拼接，决定模型每一轮能看到什么信息。这个顺序和内容直接影响模型的行为。”

“上下文管理——窗口快满了的时候，决定压缩什么、保留什么、裁剪什么。后面第 12 题会详细讲。”

【截图：Harness 职责全景；风格：checklist-card；截图目标：列出 Harness 的核心职责；关键词：Prompt组装、上下文管理、权限控制、日志审计】

“工具注册与调度——管理所有工具的 Schema，执行工具调用，处理并发。多个工具没有依赖关系的时候可以并行跑，我们的上限是 4 个。”

“权限控制——哪些工具可以自动执行（读文件），哪些需要用户确认（写文件、执行命令）。这是 Agent 落地到生产环境必须有的安全边界。”

“日志审计——每一步的输入输出都有记录，出了问题能回溯。”

“之前看到一个说法我觉得总结得挺到位的——Weak loop Strong tool。循环这部分各家做法都差不多，无非是上下文拼接和格式处理。能拉开差距的是工具能力和定制化的程度。”

### 12、上下文过长时，哪些该送、哪些该裁剪？System Prompt 怎么写？

“我们做了两层压缩。”

“第一层压缩的是短期记忆。记忆条目超过 token 预算时，用 LLM 做摘要压缩，保留关键信息，最近几轮的记忆不压缩。”

【截图：两层上下文压缩机制；风格：three-layer；截图目标：展示短期记忆压缩和对话历史压缩的两层结构；关键词：短期记忆、对话历史、摘要压缩】

“第二层压缩的是对话历史。每轮 LLM 调用前检查总 token 数，超过阈值就压缩。压缩的时候保留最近 3 轮完整交互——包括工具调用和工具返回结果，因为切断 tool_call 和 tool_result 的配对会导致模型理解出错。历史部分用 LLM 摘要替换，摘要保留：关键诉求、已完成操作、达成共识、待办事项。”

“该送的：系统指令、当前任务描述、最近几轮的工具调用和结果、用户最新输入。不该送的：已经完成的任务细节——摘要就够了；重复出现的工具调用结果；过长的工具输出——截断到关键部分就行。”

“System Prompt 写什么——角色定义、行为边界、工具使用策略、安全规则。这些在整个会话期间基本不变，放在最前面。为什么放最前面？因为 Prompt Cache 按最长公共前缀命中，静态内容越靠前、越稳定，缓存命中率越高。”

【截图：System Prompt 分层结构；风格：three-layer；截图目标：展示静态层和动态层的分层设计；关键词：静态层、动态层、Prompt Cache】

“我们的 System Prompt 分了 9 层。前 4 层是静态的——身份定义、人格层、模式层、审批层，整个会话不变。后 5 层是动态的——运行时上下文、项目记忆、Skills 索引、上下文管理策略、收尾指令，每轮都可能变。”

### 13、你了解 Prompt Cache 吗？

“Prompt Cache 的原理是按最长公共前缀缓存。”

“LLM API 收到请求后，检查当前请求的 Prompt 和最近请求的 Prompt 有多少前缀是完全相同的。相同的部分直接复用之前的计算结果，不需要重新处理，这部分输入 token 的费用大幅降低。”

【截图：Prompt Cache 命中原理；风格：whiteboard；截图目标：展示前缀匹配和缓存命中的机制；关键词：最长公共前缀、缓存命中、token成本】

“这就是为什么上一题说 System Prompt 要放在最前面。前 4 层是静态的，差不多占 Prompt 总长度的三分之一，每一轮请求都能命中缓存。动态内容放在后面，变了也不影响前缀的缓存命中。”

“假如把动态内容插到中间，前缀在动态内容的位置就断了，后面的静态内容也享受不到缓存。所以 Prompt 组装的顺序不只是逻辑上的讲究，是实实在在影响成本的。”

### 14、Vibe Coding 和 Spec Coding 有了解吗？

“Vibe Coding 是 Andrej Karpathy 提出的一个概念，大意是「凭感觉写代码」。用自然语言告诉 AI 你想要什么，AI 生成代码，你不逐行审查，跑通了就行。遇到报错就把报错信息丢给 AI，让它自己修。整个过程靠直觉驱动，不靠规格说明。”

【截图：Vibe Coding vs Spec Coding 对比；风格：data-board；截图目标：对比两种编码方式的适用场景和风险；关键词：Vibe Coding、Spec Coding、AI编程】

“Spec Coding 是另一个思路。先写规格说明——需求文档、接口定义、测试用例——然后让 AI 按规格实现。每一步都有明确的验收标准，AI 的输出可以对照规格做检查。”

“实际工作中我两个都用。做原型、试新工具、写一次性脚本的时候用 Vibe Coding，快。但做项目核心模块的时候用 Spec Coding，先把方案和接口定义写清楚再让 AI 动手。”

“生产级项目靠纯 Vibe Coding 容易翻车。代码跑通和代码正确是两回事，尤其是涉及并发、事务、权限这些场景的时候。跑通只是门槛，正确才是目标。”
