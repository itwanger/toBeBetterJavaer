## content

### 01、Agent 执行过程中工具调用失败或任务中断，恢复机制怎么设计？

“分三级来设计。”

第一级是重试。LLM API 调用失败的时候，先判断错误类型——HTTP 429（限流）、5xx（服务端错误）、连接超时、流式传输中断，这些属于临时性故障，可以重试。参数格式错误、权限不足这些重试也没用，直接返回错误让模型自己决定下一步怎么办。

【截图：三级恢复机制架构图；风格：three-layer；截图目标：展示重试、状态恢复、快照回滚三层恢复的触发条件和处理方式；关键词：指数退避、状态持久化、Git 快照】

“重试策略用指数退避加随机抖动。第一次等 500 毫秒，第二次等 1 秒，第三次等 2 秒，上限 30 秒，最多重试 3 次。加随机抖动是为了防止多个请求同时重试把服务端撞崩。如果服务端返回了 Retry-After 头，按它说的时间等。”

“工具执行失败的处理方式不一样。错误信息原样返回给 LLM，让模型自己判断——换个参数重试、换一个工具、还是直接告诉用户出了什么问题。模型做重试决策比硬编码的重试逻辑灵活得多。”

第二级是状态恢复。后台任务的执行状态用 SQLite 持久化——任务 ID、状态（排队中、执行中、已完成、失败）、输入参数、输出结果、错误信息，全部落盘。进程崩了重启之后，扫一遍所有状态为“执行中”的任务，说明崩的时候正在跑，自动改成“排队中”重新执行。

【截图：任务状态流转图；风格：swimlane；截图目标：展示任务从排队到完成的状态流转，以及崩溃后的恢复路径；关键词：状态持久化、崩溃恢复、SQLite】

第三级是快照回滚。每一轮对话开始前，给工作目录打一个 Git 快照。Agent 改了文件、跑了命令，结果发现改错了，用户一键回滚到任意一轮的状态。PaiCLI 的回滚工具就是这个机制。

#### 状态保存的粒度怎么选？

“按轮次保存。”

【截图：状态保存粒度对比；风格：data-board；截图目标：对比逐工具调用和逐轮次保存的开销和恢复精度差异；关键词：快照频率、存储开销、恢复精度】

如果按每次工具调用保存，一轮对话可能调五六次工具，快照太频繁，磁盘 I/O 开销大。按整个会话保存又太粗，中间某一轮出了问题只能全部回退。轮次级别是一个平衡点——粒度够细，用户可以精确回到出问题的那一轮；频率又不高，开销可控。

### 02、如果 Agent 分析出的故障根因存在错误，怎么重新触发诊断？

“靠执行快照实现断点续执行。”

PaiAgent 的工作流引擎在每个节点执行完之后都会保存一份快照——节点 ID、输入参数、输出结果、执行状态、重试次数。下游环节发现之前的根因分析有问题，可以从快照恢复到那个节点的状态，修改输入参数，然后重新往下执行。

【截图：断点续执行流程；风格：swimlane；截图目标：展示快照保存、断点恢复、变量修改后重跑的完整流程；关键词：执行快照、断点恢复、变量修改】

“恢复执行的时候可以修改变量。引擎接受一组修改后的输入值，替换掉快照里的旧值，从这个节点重新往下跑。已经成功完成的上游节点不需要重跑，它们的输出直接从快照里读。”

每次重新执行，快照里的重试计数加一。设一个上限，比如最多 3 次，防止同一个节点反复跑。

#### 在 LangGraph 工作流中，节点跳转条件和边界判断怎么设计？

LangGraph 用状态图来定义工作流。节点是处理单元，边是节点之间的连接，分两种。

普通边是固定跳转——A 执行完一定跳到 B。条件边是动态路由——A 执行完之后，根据输出结果里的某个字段做判断，决定跳到 B 还是 C 还是 D。

【截图：LangGraph 状态图结构；风格：whiteboard；截图目标：展示节点、普通边、条件边的关系和路由逻辑；关键词：StateGraph、条件边、分支选择】

“条件判断支持多种运算符——等于、大于等于、包含、为空。比如一个故障诊断工作流，诊断节点输出一个严重等级字段，条件边判断：等于 P0 走紧急处理，等于 P1 走常规修复，字段为空走人工审核。”

选中分支之后，没被选中的分支上的所有下游节点会被递归标记为“跳过”。递归很重要——如果 B 分支被跳过，B 后面挂着的 C、D、E 也全部跳过，不会误执行。

边界判断的原则是条件互斥加兜底完整。每条条件边的判断条件之间不能有重叠，同时要有一个默认分支兜底，所有条件都不满足时走这条路。

### 03、ReAct Agent 调外部工具时服务启动慢，同步调用还是异步调用？

“默认同步。”

ReAct 的循环是 Thought → Action → Observation → Thought，模型做下一步决策依赖工具返回的结果。工具没跑完，Observation 拿不到，循环就卡住了。这是 ReAct 模式的结构决定的。

【截图：ReAct 同步依赖示意；风格：swimlane；截图目标：展示 ReAct 循环中工具返回结果对下一步决策的依赖关系；关键词：同步等待、Observation 依赖、循环阻塞】

“多个工具之间如果没有依赖关系，可以并行。PaiCLI 用线程池并发执行，最多 4 个工具同时跑，整批超时 90 秒。但并行和异步是两回事——并行执行完了之后，所有结果还是要同步等齐了再送回 LLM。”

真正需要异步的场景是工具本身执行时间特别长——Pod 启动要几十秒、大规模数据处理要几分钟。让 ReAct 循环干等不现实。

#### 异步方案的后台任务和结果回调怎么实现？

“把慢操作拆成两个工具调用。”

【截图：异步工具调用两步模型；风格：whiteboard；截图目标：展示提交任务和查询结果的两步交互模式；关键词：submit_task、check_status、任务 ID】

第一个工具负责提交任务，把操作放进后台队列，立刻返回一个任务 ID。后台有工作线程从队列里取任务执行，状态落盘到 SQLite（排队中、执行中、已完成、失败）。

第二个工具负责查状态，传入任务 ID，返回当前状态和结果。还在跑就返回进度信息，跑完了就返回完整结果。

“Agent 提交任务拿到 ID 之后，可以先做别的事情——检查其他文件、准备下一步的参数。过一会再查状态。ReAct 循环不会被一个慢操作卡死，Agent 的时间利用率高了很多。”

### 04、多模态 RAG 系统怎么设计？

要解决的问题是怎么把不同模态的内容放到同一个向量空间里做检索。

文本 RAG 大家都熟——文档分块、向量化、检索、生成。多模态 RAG 要额外解决两件事：图片和视频怎么变成可检索的向量，以及不同模态之间怎么算相似度。

【截图：多模态 RAG 架构图；风格：whiteboard；截图目标：展示文本和图片如何统一向量化并完成跨模态检索；关键词：多模态 Embedding、统一向量空间、跨模态检索】

“两条技术路线。”

“第一条是原生多模态 Embedding。用 CLIP 系列模型，文本和图片共享同一个向量空间。输入一段文字输出一个向量，输入一张图片也输出一个向量，维度一样，直接算余弦相似度。'用文本搜图片'和'用图片搜图片'走的是同一套检索逻辑。”

第二条是模态转换。图片先用视觉模型生成文字描述，把描述当普通文本做 Embedding。好处是不需要换检索引擎，原来的文本 RAG 管线直接复用。坏处下一题会讲。

视频的处理多一步——先按固定间隔抽关键帧，每一帧当图片处理。音频部分做语音转文字。关键帧的视觉特征和音频转写的文本一起入库，检索命中某一帧时返回对应的时间戳，用户可以直接跳到视频的那个位置。

【截图：视频检索流程；风格：swimlane；截图目标：展示视频从关键帧抽取到向量入库再到时间戳定位的流程；关键词：关键帧抽取、音频转文字、时间戳定位】

“派聪明目前是纯文本 RAG，用千问的 text-embedding-v4 做向量化，2048 维，余弦相似度。如果要扩展到多模态，最直接的方式是把 Embedding 模型换成多模态版本，检索和重排序的逻辑基本不用改。”

### 05、用 LLM 生成图片描述再做文本匹配检索，有什么问题？

“信息一定会丢。”

【截图：信息瓶颈示意；风格：data-board；截图目标：展示原始图片和 LLM 描述之间的信息损失类型；关键词：空间关系、颜色纹理、数量细节】

自然语言在表达视觉信息时有天然的瓶颈。空间关系（“左上角有一个红色按钮，右下角有一段报错信息”）、精确的颜色和纹理、数量细节（“图表里有 17 根柱子”）——人眼一看就明白，文字描述很难完整保留。

还有语义偏移。同一张图片，不同的 LLM 生成的描述可能差别很大。用户检索时的措辞又是另一套表达方式。两层偏移叠加，检索准确率比原生多模态 Embedding 低不少。

成本也要算进来。入库的时候每张图片要调一次 LLM 生成描述，数据量大了之后调用费不便宜，入库速度也会慢。

“这个方案适合做兜底——多模态 Embedding 覆盖不到的场景（比如需要理解图片里的文字内容），补一层 LLM 描述。但做主检索路径不够用。”

### 06、RAG 系统的召回率 85% 怎么计算？测试集怎么构建？

“Recall@K = 检索结果命中的相关文档数 ÷ 该查询的全部相关文档数。”

举个例子。测试集里某条查询标注了 10 篇相关文档，检索返回 top-20 结果，其中有 8 篇命中了标注。这条查询的 Recall@20 就是 8 ÷ 10 = 80%。把所有测试查询的召回率取平均，得到 85%，就是整体召回率 85%。

【截图：Recall@K 计算示意；风格：data-board；截图目标：用具体数字展示 Recall@K 的计算过程；关键词：标注文档、命中数、平均值】

“K 的选择要和业务场景匹配。RAG 系统通常取 top-5 到 top-20 送给 LLM 做生成，K 设成对应的值就行。K 越大召回率越容易高，但送进 LLM 的无关内容也越多，生成质量可能反而下降。”

#### 测试集怎么构建？

“三步。”

【截图：测试集构建流程；风格：swimlane；截图目标：展示从采样到标注到验证的完整流程；关键词：分层采样、人工标注、交叉验证】

第一步，采样查询。从真实用户的历史提问里抽样，按查询类型分层——事实查询、对比查询、多跳推理查询各抽一些，保证测试集覆盖不同的检索难度。

第二步，标注相关文档。每条查询让人工标注所有相关的文档。标注要多人交叉验证，一致性低于阈值的重新标。

第三步，定期更新。知识库内容会变，新文档进来、旧文档删掉，测试集要跟着更新。

“PaiCLI 的代码搜索模块维护了一个确定性测试用例集，每条定义输入查询和预期命中的文件行号，改了搜索逻辑跑一遍就知道有没有回退。RAG 的测试集构建逻辑是一样的。”

### 07、介绍一下 LoRA 和 DPO 微调流程，训练数据是自己准备的吗？

“先说 LoRA。”

LoRA 的思路是冻结原始模型的所有权重，在需要微调的层旁边加两个小矩阵做旁路。原始权重矩阵的维度是 d × d，LoRA 把更新量分解成两个矩阵 A（d × r）和 B（r × d），r 远小于 d，一般取 8 到 64。训练时只更新 A 和 B，参数量只有原始模型的千分之几。

【截图：LoRA 低秩分解示意；风格：whiteboard；截图目标：展示原始权重矩阵和 LoRA 旁路矩阵的关系；关键词：冻结权重、低秩矩阵、旁路训练】

训练完之后，把 A × B 的结果加回原始权重矩阵，合并成一个完整模型部署。推理时和没做 LoRA 的模型结构一样，没有额外开销。

“DPO 解决的问题不一样。LoRA 教模型'怎么做'，DPO 教模型'哪个更好'。”

DPO（Direct Preference Optimization，直接偏好优化）的训练数据是偏好对——同一个输入，给两个不同的输出，标注哪个更好、哪个更差。DPO 直接用这些偏好对优化模型策略，不需要先训一个奖励模型再做强化学习。相比 RLHF 流程简单很多。

【截图：LoRA 和 DPO 的定位对比；风格：data-board；截图目标：展示两种微调方法解决的问题和数据格式差异；关键词：LoRA 能力学习、DPO 偏好对齐、RLHF 简化】

#### 训练数据怎么准备？

【截图：两种微调的训练数据格式；风格：checklist-card；截图目标：展示 LoRA 和 DPO 各自需要的数据格式和来源；关键词：指令-响应对、偏好三元组、数据质量】

LoRA 需要指令-响应对。一条数据包含输入指令（“帮我检查这段代码的 bug”）和期望的输出（完整的检查结果）。来源通常是人工标注，或者让模型生成多个回答之后人工筛选最好的那个。

DPO 需要偏好三元组——同一个输入，一个好的回答，一个差的回答。实际操作中，让模型对同一个输入生成多个回答，人工挑出最好的和最差的组成偏好对。

“数据质量比数量重要。好的数据一千条效果可能比差的数据一万条都好。”

### 08、向量数据库中的 IVF 索引原理是什么？nprobe 参数有什么影响？

IVF（Inverted File Index，倒排文件索引）的思路是分区检索——先把数据分成很多堆，查询的时候只在最可能的几堆里找。

建索引的时候，先用 K-Means 算法把所有向量聚成 N 个簇，每个簇有一个聚类中心。每个向量归入离它最近的簇，形成一个倒排列表。查询的时候，算查询向量和所有聚类中心的距离，找到最近的 nprobe 个簇，只在这几个簇的倒排列表里做精确比对。

【截图：IVF 索引结构；风格：whiteboard；截图目标：展示 K-Means 聚类后的倒排列表结构和查询时的簇选择过程；关键词：K-Means 聚类、倒排列表、nprobe 搜索】

“和暴力搜索的区别就在这里——暴力搜索要和库里每一个向量比对，IVF 只搜 nprobe 个簇里的向量。如果总共 1000 个簇、nprobe 设 10，实际只搜了百分之一的数据。”

#### nprobe 对速度和准确率有什么影响？

nprobe 越大，搜索的簇越多，准确率越高，但速度越慢。nprobe 越小，速度越快，但可能漏掉相关向量——目标向量刚好落在簇的边界，归入了相邻簇，nprobe 太小就搜不到。

【截图：nprobe 调参取舍；风格：data-board；截图目标：展示 nprobe 增大时速度和准确率的变化趋势；关键词：nprobe、准确率、查询延迟】

极端情况下 nprobe 等于簇的总数，就退化成了暴力搜索。

实际选择要看业务场景。在线场景对延迟敏感，nprobe 设小一点，牺牲一点准确率换速度。离线评测对准确率要求高，nprobe 可以设大一些。

“派聪明用的是 ES 内置的 KNN 检索，底层走的余弦相似度，和 IVF 是不同的路线。IVF 在超大规模数据上优势明显——倒排列表可以分批加载到内存，内存占用比全量加载低得多。小规模数据用 ES 的 KNN 直接搜就够了。”

### 09、Agent 应用到游戏场景做 NPC 智能交互，有哪些落地场景？怎么设计？

“三个方向比较有价值。”

第一个是动态对话 NPC。传统 NPC 对话走预设的对话树，选 A 走 A 分支，选 B 走 B。Agent 驱动的 NPC 可以自由对话——玩家说什么它都能接住，回复基于当前剧情、玩家进度和 NPC 自身的人设生成。

【截图：动态对话 NPC vs 传统对话树；风格：data-board；截图目标：对比传统对话树和 Agent NPC 在灵活度上的差异；关键词：对话树、自由对话、人设一致性】

第二个是任务引导 NPC。玩家卡关了，Agent 根据玩家当前的装备、等级、已完成任务给出针对性的提示，每个玩家收到的提示都不一样。

第三个是战术 AI 队友。组队副本里，AI 队友根据战场实时情况做决策——治疗谁、优先打哪个怪、什么时候用技能。比传统的行为树 AI 灵活得多。

#### 整体方案怎么设计？

“三层架构。”

【截图：游戏 NPC Agent 三层架构；风格：three-layer；截图目标：展示感知层、决策层、执行层的职责和数据流；关键词：游戏状态感知、LLM 决策、游戏 API 执行】

感知层负责把游戏状态翻译成 LLM 能理解的文本。玩家位置、周围环境、背包物品、对话历史，格式化成一段描述文本送给模型。

决策层是 LLM 推理。给定当前状态和 NPC 人设，输出下一步行动——说一句话、移动到某个位置、释放某个技能。对话场景可以容忍一两秒延迟，战斗决策可能要控制在几百毫秒以内，对模型的推理速度要求不一样。

执行层把 LLM 的决策翻译成游戏引擎的 API 调用。“移动到坐标 (100, 200)”变成引擎的移动指令，“释放火球术”变成技能调用。

“成本控制绕不开。一个场景里可能同时有几十个 NPC，每个都实时调大尺寸模型 token 消耗很高。做法是分级——重要的剧情 NPC 用大尺寸模型保证对话质量，普通路人 NPC 用小尺寸模型或者规则引擎兜底。对话频率也要限制，NPC 不需要对玩家的每一个动作都做出反应。”

### 10、平时用 AI Coding 工具吗？公司限制国外大模型 API 怎么办？

“日常主力是 Claude Code 和 Codex。复杂任务用 Claude Code，上下文工程和工具调用做得好，大规模重构这类活效率很高。Codex 适合快速的代码修改，在 IDEA 里用插件直接调。”

【截图：AI Coding 工具选型；风格：skill-card；截图目标：展示主力工具和国内替代方案的定位差异；关键词：Claude Code、Codex、WorkBuddy、DSH】

“限制国外 API 的话，国内替代方案不少。WorkBuddy 是腾讯从 CodeBuddy 演化出来的，月活已经过千万，产品体验做得不错。DSH 是 DeepSeek 自己的终端 Agent。Qoder 是阿里的 AI Coding 工具。这三个都可以直接替代日常开发。”

还有一条路是 Harness 加国产模型。Claude Code 和 Codex 其实就是 Harness——外层负责工具调用、上下文管理、循环控制，内层调模型做推理。把模型 API 换成千问、DeepSeek、混元这些国产模型的接口，Harness 层的工程能力不受影响。开源的 Harness 项目已经有不少了，部署在公司内网就能用。

**核心职责**：

- 设计三级容错恢复机制，工具级指数退避重试（3 次 + 随机抖动）、任务级 SQLite 状态持久化（启动自动恢复中断任务）、会话级 Git 快照回滚，保障长会话执行的稳定性

- 搭建三层效果评估体系，维护确定性测试用例集，结合 LLM-as-Judge 批量评分和人工校准抽检，保障迭代不回退
