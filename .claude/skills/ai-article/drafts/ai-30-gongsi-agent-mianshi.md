## content

### 01、系统如何区分正常重试和无效循环？「有没有取得进展」用什么指标判断？

「我在 PaiCLI 里做了一套工具签名的滑动窗口机制来检测循环。」

每一轮 Agent 调用完工具之后，系统会把这一轮的工具调用生成一个签名，签名由工具名加上参数拼接而成。比如说调用了 read_file，参数是 /src/Main.java，这就是一个签名。

系统维护了一个固定大小的滑动窗口，默认窗口大小是 3。每轮新签名进来，窗口往前滑一格。

如果窗口里的 3 个签名完全一样，就判定为停滞，触发 STAGNATION_DETECTED 退出。

【截图：工具签名滑动窗口检测机制；风格：swimlane；截图目标：展示签名生成、窗口滑动和停滞判定的完整流程；关键词：工具签名、滑动窗口、STAGNATION_DETECTED】

「参数也要算进签名，因为同一个工具做不同的事，算有进展。」

举个例子，Agent 连续三次调用 grep_code，但每次搜的关键词都不一样，说明它在尝试不同的检索策略，这算正常重试。只有工具名和参数都完全一样的时候，才说明 Agent 卡住了，在做无意义的重复。

窗口大小可以通过配置项调整，太小容易误判，太大又反应迟钝。默认值 3 是实测下来比较合理的平衡点。

#### 为什么用工具签名而不是对比 LLM 输出文本来判断循环？

LLM 每次生成的文本都有随机性，即使在做完全重复的事情，输出的措辞也会有差异。拿文本做相似度比较需要设一个阈值，阈值高了漏检，低了误报。

工具调用是结构化的，工具名和参数是精确字符串，要么完全一样，要么不一样，没有模糊地带。判断起来简单可靠，不需要额外的相似度计算。

### 02、Agent 达到最大执行轮数但已完成部分工作，是直接退出还是返回部分结果？

「要分执行模式来说。」

ReAct 模式是最基本的单 Agent 循环。达到硬上限之后，默认是 50 轮，直接返回一条错误信息告诉用户执行超限了。

不会抛异常，但也不会把中间的工具输出拼成部分结果返回。ReAct 模式的对话历史里已经包含了所有工具调用和返回值，用户可以回看 Agent 之前做了什么。

Plan 模式不一样。每个子任务有自己的执行上限，默认 5 轮。

如果某个子任务跑满了，系统会把已经积累的工具输出拼成一个字符串返回。后面的子任务如果依赖这个结果，拿到的就是部分结果，不是空值。

【截图：三种执行模式的超限处理对比；风格：data-board；截图目标：对比ReAct、Plan、多Agent三种模式在超限时的行为差异；关键词：ReAct、Plan、多Agent、部分结果】

多 Agent 模式的处理更温和。每个步骤最多重试 2 次，重试用完之后，系统会保留当前已有的结果，打个警告标记，然后继续执行后面的步骤。

「能救多少救多少，已经做完的工作不要浪费。」

Plan 模式和多 Agent 模式都选择了保留部分结果，因为这两种模式的任务本身就是可拆分的。一个子任务没跑完不代表整个计划要作废，其他子任务的产出可能已经够用了。

### 03、项目中哪些是自己开发的？哪些复用现成的框架？

「PaiCLI 没有用任何 AI 框架，全部自研。」

ReAct 循环、工具调度、Prompt 组装、上下文压缩、记忆系统、多 Agent 编排、Skill 体系，这些全是从零写的。MCP 客户端也是自己实现的，包括 JSON-RPC 协议层和传输层，stdio 和 Streamable HTTP 都支持。

用到的第三方库都是工具级别的。OkHttp 做 HTTP 请求，Jackson 做 JSON 序列化，SQLite 做持久化存储，JavaParser 做代码 AST 解析，JGit 做 Git 操作，Lanterna 做终端 TUI 渲染，Jieba 做中文分词。

【截图：PaiCLI技术栈全景——自研模块 vs 工具库；风格：three-layer；截图目标：让读者看到哪些是自研的核心能力，哪些是复用的基础设施；关键词：自研、工具库、模块分层】

平场我做 PaiCLI 的时候也考虑过 Spring AI 和 LangChain4j。但终端 Agent 对启动速度、内存占用和响应延迟都比较敏感，Spring 全家桶的启动开销太大了。

LangChain4j 的抽象层级又和我想要的 Prompt 组装方式对不上，与其适配框架的接口，不如直接写。工具调用、MCP 协议这些东西的逻辑并不复杂，手写的代码量也就几千行。

自研之后每一层都能按需调整，比如说 Prompt 分层缓存的策略、上下文压缩的触发时机，这些如果用框架反而改起来费劲。

### 04、多 Agent 协同执行时可能遇到哪些性能瓶颈？如何解决？

「LLM API 调用延迟是最大的瓶颈。」

多 Agent 编排里，每个 Worker 每一轮都要调一次 LLM。一次 LLM 调用快的话一两秒，慢的话十几秒。

两个 Worker 并行跑 5 轮，就是 10 次 LLM 调用，这个延迟是省不了的。

共享资源的锁竞争同样值得注意。PaiCLI 的多 Agent 模式里，对话历史是隔离的，每个 Worker 有自己的消息列表。

但工具注册表和记忆管理器是共享的，多个 Worker 同时读写记忆，或者同时查询 MCP 工具列表，会产生竞争。

【截图：多Agent资源共享与隔离架构；风格：whiteboard；截图目标：展示哪些资源共享、哪些隔离，以及锁竞争出现的位置；关键词：对话隔离、工具注册表共享、记忆锁竞争】

Worker 用 BlockingQueue 做池化，空闲 Worker 自动领取下一批任务。规划器生成的执行计划会被解析成 DAG，按拓扑排序分批调度，同一批内的任务没有依赖关系，可以安全地并行。

审查器不碰工具，这是一个设计上的约束。规划器和审查器只做判断，不执行工具调用，工具执行权集中在 Worker 手里。

这样就避免了审查器一边审查一边改代码的情况。

### 05、如何控制 Agent 并发数量？有哪些限流或调度策略？

「多 Agent 编排模式用 BlockingQueue 做 Worker 池化。」

系统默认创建 2 个 Worker，线程池大小也是 2。每批可并行执行的任务数取决于当前空闲 Worker 的数量。

Worker 执行完一个步骤后自动归还到队列里，下一个步骤可以立即领走。

Plan 模式用固定线程池，上限 4 个并行任务。每一批拓扑排序后依赖已满足的任务，取任务数和 4 的较小值作为并行度。

【截图：不同执行模式的并发控制策略对比；风格：data-board；截图目标：对比多Agent、Plan、后台任务三种模式的线程池大小、调度方式和并发上限；关键词：BlockingQueue、线程池、FIFO】

后台任务队列用的是 FIFO 轮询机制。Worker 数量通过配置项控制，默认 2 个，每个 Worker 以 300 毫秒为间隔轮询 SQLite 数据库，取出状态为待执行的任务来跑。

「没有做速率限制，并发完全靠线程池大小来控制。」

PaiCLI 是本地运行的工具，不存在多用户抢占的问题。并发的上限受限于 LLM API 的并发配额，线程池大小设成 2 到 4 已经够用了，再大反而会被 API 限流。

#### PaiCLI 怎么写到简历上？

项目名称：CodeMate——Agent CLI 编程助手 2026.03 – 2026.05

项目简介：面向 Java 项目的本地 CLI 编程 Agent，支持自然语言驱动代码检索、任务规划、代码修改及自动诊断，集成 Multi-Agent、代码检索、长期记忆及安全执行能力，实现从需求分析到代码交付的自动化开发流程。

技术栈：Java 21、JLine、JavaParser、SQLite、JGit、Ollama、Jieba

【截图：PaiCLI简历项目亮点提炼；风格：skill-card；截图目标：展示简历中核心职责的提炼思路；关键词：简历包装、核心职责、量化数据】

核心职责：

- 设计 ReAct 与 Plan-Execute 双模式执行框架，简单任务采用 ReAct 完成工具调用与迭代推理，复杂任务拆分为 DAG 并由调度器按依赖关系并行执行；结合 Planner、Worker、Reviewer 多 Agent 协作，根据审查结果自动修复失败节点并控制重试次数，提高复杂开发任务执行成功率。
- 构建代码仓库检索能力，优先通过 ripgrep 快速定位代码，再结合 JavaParser 按类、方法生成 AST 索引，并融合 Ollama Embedding、Jieba、BM25 等方式完成语义检索与关键词检索，实现跨文件代码定位；在千级代码块规模下检索 P90 延迟保持在 94ms。
- 设计短期、长期双层记忆机制，将对话、工具结果及任务状态分别管理，并采用 Map-Reduce 对历史上下文进行摘要压缩；长期记忆基于 SQLite 持久化，结合 BM25 与向量检索动态召回相关历史，提高跨会话代码开发连续性。
- 基于 Git Worktree 为每个任务创建独立工作区，并结合 Side-Git 保存执行过程中的代码快照；通过 Diff 与 Java LSP 自动收集代码修改及诊断结果反馈给 Agent，在保证任务隔离的同时支持失败恢复与增量修复。
- 建立 Java Code Agent 自动评测体系，基于 SWE-bench Multilingual 与 Harbor 构建 43 个真实开源 Issue 测试集，在固定代码版本及隔离环境下自动验证 Patch，成功修复 27 个任务，Pass@1 达到 62.8%。

### 06、直播场景大量用户同时点赞，如何优化？

「点赞这种高频低价值的操作，最忌讳每一次都落库。」

用户在直播间疯狂点屏幕，一秒钟可能点好几十次。如果每一次点击都直接打到数据库，数据库先扛不住。

客户端先做合批。用户点了多少次先在本地攒着，比如说每隔 500 毫秒或者累计 20 次，把一个合并后的增量数字发给服务端。

这样一个用户的点赞请求从每秒几十个变成每秒两个。

【截图：点赞请求的客户端合批与服务端聚合流程；风格：swimlane；截图目标：展示从用户点击到最终落库的完整数据流；关键词：客户端合批、Redis INCRBY、异步落库】

服务端收到请求后用 Redis 的 INCRBY 做原子累加，不走数据库。Redis 单线程模型天然避免了并发问题，INCRBY 的吞吐量轻松扛住百万级 QPS。

然后用一个定时任务，比如说每 5 秒把 Redis 里的计数批量刷回数据库。这一步走异步，数据库的写入压力降了好几个量级。

「前端展示不需要精确实时。」

用户看到的点赞数用动画补间来过渡，从当前值平滑地增长到最新值。差个几秒钟，用户感知不到。

直播间的点赞本来就是烘托氛围用的，精确到个位数没有意义。

### 07、目前 RAG 最大的瓶颈是什么？

「检索质量。模型再强，检索不准就是白搭。」

RAG 的流程是先检索再生成。如果检索阶段召回的文档和用户问题不相关，后面的大模型拿着一堆无关内容去生成回答，质量不可能好。

【截图：RAG流程中检索质量对生成质量的影响；风格：three-layer；截图目标：展示检索不准时生成质量如何下降；关键词：检索召回、噪音文档、生成质量】

分块粒度直接影响召回质量。切得太粗，一个 chunk 里混了好几个主题，召回之后噪音太多。

切得太细，语义断裂，模型理解不了上下文。拿我做派聪明 RAG 知识库的经验来说，512 字符加 100 字符重叠是一个比较稳妥的起点，具体还要看文档类型调整。

Embedding 模型的选择也很关键。同样一句话，不同 Embedding 模型编码出来的向量质量差别很大。

选模型的时候要看 MTEB 榜单和实际业务的匹配度，不能只看跑分。

查询改写同样不能忽视。用户的原始问题经常很口语化，甚至有错别字。

不做改写直接拿去检索，召回率会打折扣。可以用大模型做一次 query rewriting，把口语化的问题转成更精确的检索查询。

### 08、给电商平台搭建百万级商品知识库问答系统，怎么设计？

「标准的 RAG 架构，但规模上去之后，每一层的选型和参数都要仔细调。」

文档处理层负责把商品数据变成可检索的 chunk。商品信息通常包含标题、描述、参数表和用户评价，每种内容的切分策略不一样。

标题和参数表按字段切分，描述和评价按语义段落切分。分块大小用 512 字符，重叠 100 字符，不足 100 字符的短块合并到前一个 chunk 里。

【截图：电商知识库RAG架构分层设计；风格：whiteboard；截图目标：展示从商品数据到用户问答的完整架构；关键词：文档处理、混合检索、生成层】

Embedding 选阿里 DashScope 的 text-embedding-v4，2048 维。批量处理的时候每批 10 条，加上重试和指数退避，避免 API 限流导致的数据丢失。

检索层用混合检索。ES 先做 KNN 向量召回，召回窗口设成 topK 乘以 30，比如说要 5 条结果就先召回 150 条候选。

然后在候选集上做 BM25 关键词匹配重排序，KNN 权重 0.2，BM25 权重 1.0。

「BM25 权重比向量高，因为电商场景里用户经常搜具体的型号、品牌和参数，关键词匹配在这种场景下比语义相似度更准。」

权限隔离用三级控制。ES 查询里加一个 bool should，同时匹配用户私有数据、公开数据和组织级数据。

组织标签支持层级继承，上级组织的数据下级也能访问。

【截图：混合检索流程——KNN召回加BM25重排序；风格：swimlane；截图目标：展示从用户查询到最终返回结果的检索流程；关键词：KNN、BM25、权限过滤】

生成层用 DeepSeek V4 做回答生成，temperature 设 0.3，偏保守。检索结果包在特定标记之间注入 Prompt，强制模型基于检索内容回答，减少幻觉。

#### 为什么选混合检索而不是纯向量检索？

纯向量检索在语义理解上很强，但对精确关键词不敏感。

用户搜「iPhone 16 Pro Max 256GB 价格」，这里面每一个词都是精确匹配的关键信息。纯向量检索可能会把「iPhone 15 Pro 512GB」也召回来，因为语义上确实很近。

但用户要的就是那个具体型号和容量。

BM25 擅长的就是这种精确匹配。把 BM25 和向量检索组合起来，向量负责理解意图，BM25 负责锚定关键词。

### 09、商品信息动态更新，知识库设计需要考虑什么？

「商品价格可能一天改好几次，描述也经常调整，知识库必须能跟上这个变更频率。」

每次商品信息变更的时候，先算一个文件指纹，用 MD5 就行，和上一次入库时的指纹对比。指纹一样说明内容没变，跳过。

不一样的话，只对变更的部分重新分块和重新生成 Embedding，不用全量重跑。

【截图：商品信息增量更新机制；风格：swimlane；截图目标：展示从变更检测到索引更新的完整流程；关键词：MD5指纹、增量分块、版本标记】

版本管理也要做。每个 chunk 带一个版本字段，更新的时候新版本入库，旧版本打个标记但不立即删除。

查询的时候只命中最新版本。

为什么不直接删旧版本？因为 ES 的删除操作是异步的，如果删除和查询并发执行，可能出现短暂的数据空白。保留旧版本用版本字段过滤，更稳妥。

触发机制上用双保险。商家后台修改商品信息的时候发 Webhook 通知知识库服务，做实时增量更新。

同时跑一个定时任务，比如说每小时全量扫一遍，兜底那些 Webhook 漏掉的变更。

### 10、测试说你的接口有问题，你会怎么做？如何排查？

「先复现，不是先看代码。」

找测试同学要清楚入参、请求环境、操作步骤和返回结果。拿到这些信息之后自己跑一遍，看能不能复现。

能复现的 bug 就已经解决了一半。

如果能复现，直接看日志。先定位到请求对应的日志行，看有没有异常堆栈。

有堆栈的话，顺着堆栈找到出问题的代码位置，分析入参在那个位置为什么会触发异常。

【截图：接口问题排查流程；风格：swimlane；截图目标：展示从收到反馈到修复上线的完整排查过程；关键词：复现、日志定位、数据流追踪】

如果日志里没有异常，说明代码没报错但返回了不对的数据。这种情况需要跟数据流，从接口入口开始，看每一步数据经过了哪些处理，在哪一步变成了不符合预期的样子。

可以加临时日志或者用断点调试。

「复现不了的情况也很常见。」

先排除环境差异。测试用的环境和自己的开发环境，数据库、配置、依赖版本是不是完全一致。

有些 bug 只在特定数据组合下才会触发，单独构造测试同学描述的那组数据试一下。

修完之后补一个回归测试用例，把这次的入参和预期结果固化下来。下次有人改了相关代码，测试会自动拦住。
