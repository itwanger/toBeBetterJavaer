### 01、简单介绍一下自己的经历，以及之前参与过的 AI Agent 相关工作？

“做过三个 Agent 方向的项目。”

【截图：三个Agent项目全景；风格：whiteboard；截图目标：展示候选人三个项目的定位和技术栈关系；关键词：PaiCLI、派聪明、PaiAgent】

“PaiCLI 是一个终端 Agent，对标 Claude Code，用 Java 和 Spring AI 实现。支持三种执行模式：ReAct 处理日常交互，Plan-and-Execute 处理需要分步骤的复杂任务，Multi-Agent Team 让规划器、执行器、审查器三个角色协作。内置了代码搜索、文件读写、命令执行、MCP 工具调用这些能力。”

“派聪明是一个 RAG 知识库，基于 Elasticsearch 做混合检索——向量检索负责语义匹配，BM25 负责关键词精确匹配，两路结果加权合并。支持 PDF、Markdown 等格式的文档上传和自动分块。”

“PaiAgent 是一个可视化的 Agent 工作流编排平台，后端用 LangGraph4j 做状态图引擎，前端用 ReactFlow 做拖拽式节点编排，支持 ReAct Agent 节点、LLM 节点、检索节点等不同类型的执行单元。”

### 02、Coding Agent 的记忆怎么做的？

“记忆分两层：长期记忆和短期记忆。”

“长期记忆有两种形式。一种是事实记忆，存在本地 JSON 文件里，有项目级和全局两种作用域。每轮 LLM 调用之前，记忆检索模块根据用户当前的输入查询相关记忆条目，匹配上的才注入系统提示词，注入量有 token 预算控制。”

【截图：长期记忆与短期记忆架构；风格：three-layer；截图目标：展示长期记忆（事实记忆+项目规范）和短期记忆的层级关系和数据流向；关键词：长期记忆、短期记忆、PAI.md】

“另一种是项目规范，通过 PAI.md 文件注入。四个文件按优先级依次加载：PAI.md → .paicli/PAI.md → PAI.local.md → .paicli/PAI.local.md，后面的覆盖前面的。存的是项目级别的规范和约定——代码风格、技术栈要求、安全策略这些。和事实记忆不同的是，PAI.md 每轮都会全量注入，不走检索，也不参与压缩。”

“短期记忆就是对话历史，做了两层压缩。”

“第一层压记忆条目。当短期记忆的 token 数超过预算时，用 Map-Reduce 策略加 LLM 摘要，把旧的记忆条目合并压缩，保留最近 N 轮不动。”

“第二层压对话历史。触发条件是当前 token 数超过上下文窗口的安全线——200k 的窗口大约在 167k 左右触发。压缩时找到所有 user 消息的位置，保留最近 3 轮用户消息和它们对应的完整交互，包括 tool_call 和 tool_result，不会把一对工具调用拆开。历史部分用 LLM 生成摘要替换，摘要强制保留四类信息：用户的核心诉求、已完成的操作、达成的共识、还没做的事情。”

【截图：两层压缩流程；风格：swimlane；截图目标：展示记忆条目压缩和对话历史压缩的触发条件与处理步骤；关键词：Map-Reduce、保留最近3轮、摘要替换】

“为什么不全量注入——两个原因。系统提示词越长，Prompt Caching 命中率越低，PaiCLI 把静态内容排在 prompt 开头，缓存按最长公共前缀匹配，前缀越稳定命中率越高，动态记忆塞多了反而拉高 token 成本。另外长上下文有 Lost in the Middle 的问题，中间部分模型关注度低，塞太多记忆在中间，真正相关的那条容易被忽略。绝大多数对话其实只需要一两条相关记忆，按需检索注入是更合理的方案。”

### 03、你们的 Agent 和 Claude Code、Codex 有什么区别？

“PaiCLI 的整体架构就是参照 Claude Code 做的，执行模式基本对齐——ReAct 循环、Plan 模式、Sub-agent 多 Agent 协作都有。Claude Code 还多了一个 Goal 模式，设定完成条件后自主执行直到目标达成，这个 PaiCLI 暂时没做。”

【截图：三款 Coding Agent 对比；风格：data-board；截图目标：直观展示 Claude Code、Codex、PaiCLI 在部署形态、模型绑定、实现语言三个维度的差异；关键词：Claude Code、Codex、PaiCLI】

“和 Codex 的差异更大一些。Codex 现在有 CLI、桌面应用、Cloud 和 Web 四种形态。CLI 和桌面应用在本地执行代码，跟 Claude Code 一样；Cloud 模式是每个任务启动一个云端沙箱，代码在远端容器里跑。Claude Code 和 PaiCLI 都是纯本地终端工具，没有云端执行的选项。”

“最大的区别在模型绑定。Claude Code 绑定 Claude 系列，Codex 绑定 OpenAI 系列，都只能用自家模型。PaiCLI 做了模型抽象层，通过工厂模式创建客户端，DeepSeek、智谱、Kimi 这些都能接，改个配置就切换。PaiAgent 还额外对接了火山引擎，可以用豆包的模型。”

“自研的意义就在这里——模型选择自由，不被单一厂商绑定，上下文策略和工具集也能按自家业务需求定制。”

### 04、你们怎么对 Agent 去做评测的？

“结果层看任务成功率。评测环境必须可复位，每次从同一个初始状态出发，上一次运行产生的副作用不能留到下一次。否则同一个用例跑第一次和跑第十次结果可能完全不一样，评测没有意义。”

“过程层看效率。完成同一个任务用了多少步、消耗了多少 token、工具调用成功率多少。两个 Agent 都能做完任务，一个 3 步搞定，另一个绕了 12 步，水平差距就在这里。”

【截图：三层评测指标；风格：three-layer；截图目标：展示结果层、过程层、稳定性层的层级关系和具体指标；关键词：任务成功率、步数效率、方差】

“稳定性层看方差。同一个任务跑多次，结果一致性如何。10 次里 7 次成功 3 次失败，说明某个环节有不确定性，需要排查是提示词的问题还是模型本身的波动。”

“PaiCLI 的代码搜索模块维护了一个 Golden Set，里面是确定性测试用例——定义好输入 query 和预期命中的文件行号，跑一遍就知道搜索效果有没有回退。每次改完提示词或切了模型，先跑 Golden Set。”

“大批量评测用 LLM-as-Judge，定义评分标准让模型打分，成本低、速度快。但模型裁判自己会有位置偏好——PaiCLI 做了位置平衡的 A/B 对比，把两个 Agent 的产出分别放在 A 和 B 的位置让模型打分，然后交换位置再打一次，两次结果不一致的降级为平局。”

【截图：位置平衡 A/B 评分流程；风格：swimlane；截图目标：展示 A/B 交换位置打分、不一致降级为平局的流程；关键词：位置平衡、A/B 对比、一致率校准】

“定期还要做人工校准。随机抽一批模型裁判打过分的样本，人工复审，算两边的一致率。一致率低了，要么评分标准需要调整，要么模型裁判用的基座模型自己漂移了。”

### 05、云 Agent 如果容器迁移或者重启了，上下文信息怎么办？

“把所有状态外置，容器本身做成无状态的。”

“对话历史做 Redis 加数据库双写。Redis 存热数据，最近的对话轮次，访问快，设一个过期时间。数据库存完整历史，永久保留。容器重启后先从 Redis 恢复最近对话，Redis 也丢了就从数据库兜底。”

“任务计划持久化到数据库。执行计划里每个任务都有状态标记——等待中、执行中、已完成、失败。重启后读取执行计划，找到最后一个‘执行中’或‘等待中’的任务，从那里继续。已完成的不会重做。”

【截图：状态外置与容器恢复架构；风格：whiteboard；截图目标：展示 Redis + DB 双写、共享存储、checkpoint 的整体架构；关键词：状态外置、Redis 双写、Checkpoint】

“文件系统状态挂共享存储。容器本地磁盘是临时的，重启就没了。工作区目录需要挂载到共享文件系统或对象存储，代码和中间产物不会因为容器迁移而丢失。”

“再加一个 checkpoint 机制。每完成一个任务做一次状态快照——当前的对话摘要、已完成任务列表、工作目录的文件变更清单——写到数据库。恢复时加载最近的 checkpoint，同步文件状态，继续执行。checkpoint 粒度按任务走，每个 task 完成后做一次，对写文件、执行系统命令这些可能产生副作用的操作，在操作前额外做一次，确保操作失败时能回到操作前的状态。”

【截图：Checkpoint 触发策略；风格：checklist-card；截图目标：说明任务粒度和关键操作粒度的触发时机；关键词：任务粒度、关键操作、恢复成本】

### 06、Goal 这里怎么做任务持续推进而不行为漂移？

“目标固定是最基本的。用户的原始目标放在系统提示词的静态层，模型每一轮都能看到。不是放在对话历史里——对话历史会被压缩，目标可能被摘要稀释掉。静态层永远不会被压缩，目标始终完整地摆在那里。”

【截图：目标固定与任务推进机制；风格：whiteboard；截图目标：展示目标存储位置和防漂移机制的协作关系；关键词：目标固定、任务列表、范围守卫、压缩保留】

“然后是结构化任务列表。Plan 模式会把目标拆解成一个带依赖关系的任务列表，每个任务有明确的描述和状态。模型每一轮看到的信息里包含哪些任务做完了、哪些在等待、当前在做第几个。做完一个划掉一个，下一步该做什么一目了然，就像看板一样。”

“范围守卫也要做。系统提示词里有明确指令——如果当前操作偏离了主线目标，停下来重新评估。配合工具调用的审批机制，写文件、执行命令这些高风险操作需要确认，偏离在早期就能拦住。”

“还有压缩时保留目标。对话历史压缩的摘要模板强制保留四类信息：核心诉求、已完成操作、达成共识、待办事项。核心诉求就是用户的原始目标，压缩多少轮都在摘要里。而且目标信息存了两份——系统提示词的静态层一份，压缩摘要的核心诉求字段一份。压缩只动对话历史的中间部分，最近 3 轮完整保留，系统提示词完全不动，双份冗余保证目标不会丢。”

【截图：目标信息双冗余存储；风格：three-layer；截图目标：说明系统提示词静态层和压缩摘要的双保险机制；关键词：静态层、压缩摘要、双冗余】

### 07、Coding Agent 接的什么模型？

“PaiCLI 做了模型抽象层，通过工厂模式创建 LLM 客户端，目前支持 DeepSeek、智谱、阶跃星辰、Kimi 等。PaiAgent 额外接了火山引擎，可以用豆包的模型。切模型只需要改配置，不用动代码。”

【截图：模型选择三个指标；风格：data-board；截图目标：展示代码生成质量、工具调用准确率、上下文窗口大小三个选型维度；关键词：代码生成、工具调用、上下文窗口】

“选模型看三个指标。代码生成质量——Coding Agent 的核心动作就是写代码，这一项直接决定任务成功率。工具调用准确率——Function Calling 参数格式对不对、调用时机准不准，影响整条工具链的可靠性。上下文窗口大小——窗口太小的话多文件编辑时上下文装不下，压缩频率变高，信息损失就大。就目前来说，200k 以上的窗口才比较够用。”

“成本控制靠 Prompt Caching。静态内容（身份定义、工具描述、安全策略）固定排在 prompt 最前面，整个会话不变，缓存命中率高。缓存命中和没命中的价格差能到数十倍，省下来的成本很可观。另外可以做分层模型策略，复杂任务用大尺寸模型，简单任务用小尺寸模型，按任务难度动态切换。”

### 08、你认为在模型能力强的前提下，Agent 最重要的是什么？

“Harness 的质量。Harness 就是模型外面的工程外壳——工具定义、权限控制、上下文管理、错误恢复这些。”

“Agent 的 ReAct 循环本身很简单——接收输入、调用模型、执行工具、观察结果、再调用模型——谁写都差不多。差距出在 Harness 里的工程细节。”

【截图：Harness 三个能力；风格：three-layer；截图目标：展示约束边界、错误恢复、上下文管理的层级关系和具体作用；关键词：约束边界、错误恢复、上下文管理】

“约束边界。工具有白名单，路径有访问限制，写文件和执行命令走审批。模型能力越强，没有约束时犯错造成的破坏越大——它可以删掉不该删的文件，执行不该执行的命令。这些约束保护的是用户。”

“错误恢复。工具调用失败了能自动重试，文件改坏了能回滚。PaiCLI 做了 Side-Git 快照，每次写文件前自动存一份，改坏了用工具一键恢复。没有恢复机制的话，一次工具调用报错可能让整个任务跑偏，后面全在错误的基础上干活。”

“上下文管理。该给模型看什么、不该看什么。一个 grep 搜索返回几百行结果，全塞给模型，中间的内容大概率被忽略。好的 Harness 会做摘要和筛选，把关键信息放在模型注意力集中的位置。”

### 09、模型注意力的上下文 Lost in the Middle 你了解什么原理吗？

“Lost in the Middle 是 2023 年 Nelson F. Liu 等人发表的研究发现。”

“他们做了一个实验，把相同的相关文档分别放在长上下文的不同位置，测试模型的回答准确率。结果发现，LLM 处理长上下文时注意力分布呈 U 形——放在开头的文档准确率大约 75%，放在中间的降到大约 55%，差了 20 个百分点。”

【截图：U 形注意力分布；风格：data-board；截图目标：展示开头、中间、结尾三个位置的准确率差异和 U 形曲线；关键词：U 形分布、75% vs 55%、位置影响】

“更极端的情况——给模型塞 20 篇参考文档，效果反而不如一篇都不给。中间的噪音把有用信息淹没了，比闭卷回答还差。”

“原因和 Self-Attention 的计算方式有关。每个 token 要和上下文里所有其他 token 计算注意力权重，计算量是 O(n²)。位置编码（比如 RoPE）根据 token 所在位置施加旋转变换，不同位置的 token 在注意力计算中的贡献不同。训练数据的分布也有影响——文档开头通常是摘要、结尾是结论，信息密度比中间高，模型在训练过程中学到了对头尾位置投入更多注意力这个模式。”

“对 Coding Agent 来说影响很直接。长上下文里包含多个文件的代码，中间文件的分析结果容易被忽略。工具调用返回大量搜索结果，排在中间的结果可能被模型跳过。多轮对话中，早期的重要上下文被压到了中间位置，模型可能忘了之前做过的决策。”

【截图：Coding Agent 应对 Lost in the Middle 的方案；风格：checklist-card；截图目标：展示关键信息放两端、上下文压缩、Sub-agent 隔离三个策略；关键词：信息放两端、上下文压缩、Sub-agent 隔离】

“应对方案有三个。第一，关键信息放两端——系统提示词在上下文开头，当前任务和最近一轮交互在结尾，中间放的是可以被适度忽略的历史信息。第二，上下文压缩——不等窗口塞满才压缩，差不多占到窗口的 80% 就触发，压缩中间的历史对话，保留最近几轮完整内容。第三，Sub-agent 隔离——多文件编辑这种大任务，拆成多个 Sub-agent，每个只处理一个模块，各自拿到独立的上下文窗口，主 Agent 只接收结果摘要，避免中间堆积大量代码。”

### 10、场景题：如果希望通过 Agent 实现广告投放策略的自动优化，你会怎么设计？

“整体分三个模块：数据采集、策略分析、执行调整，用一个反馈回路串起来。”

【截图：广告投放 Agent 整体架构；风格：whiteboard；截图目标：展示数据采集→策略分析→执行调整→反馈回路的整体流程；关键词：数据采集、策略分析、执行调整、反馈回路】

“数据采集模块负责从广告投放平台拉数据。字节系的话就是巨量引擎的 API，定时拉取各维度指标：展示量、点击率、转化率、单次转化成本、ROI。除了自身投放数据，还采集行业基准做对比参照。数据拉回来后做清洗和异常检测——比如某个计划的点击率突然暴增，可能是异常流量，需要标记出来，避免干扰后续的策略判断。”

“策略分析模块是核心。拿到数据后做多维度归因分析：哪些素材的点击率高、哪些受众群体的转化好、哪些投放时段的 ROI 更优。归因结果交给策略生成 Agent，输出具体的优化建议——‘计划 A 的素材点击率低于均值，建议替换主图’或者‘计划 B 在凌晨时段的转化成本过高，建议降低该时段出价’。建议要可执行，具体到哪个计划、改什么参数、改成多少。”

“执行模块调用广告平台的 API 执行调整，但不能直接全量生效。新策略先在小流量上做 A/B 测试——抽一部分预算按新策略投放，和原策略对比效果。效果达标之后灰度放量，逐步从小比例提到全量。”

【截图：A/B 测试与灰度放量流程；风格：swimlane；截图目标：展示新策略从小流量测试到全量生效的分阶段流程；关键词：A/B 测试、灰度放量、止损暂停】

“两个关键设计。第一，预算变更必须走人工审批。Agent 可以调出价、换素材、改定向，但涉及预算增减的操作，必须推送给投放同学确认后才执行。投放预算是真金白银，不能让 Agent 全权决定。第二，止损机制。如果某个计划调整后 ROI 连续低于设定的阈值，自动暂停该计划并报警，等人工介入排查。”

“反馈回路是定时刷新数据——比如每小时拉一次——重新评估当前策略的效果。效果持续好的维持不动，效果回落的触发新一轮分析和调整。日报汇总全天的调整记录和效果对比，周报做趋势分析，帮投放团队看清整体走势。”
