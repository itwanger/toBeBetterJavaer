# 深度拆解类规范

主参考全文见 `claude-code-grep-vs-rag.md`。

深度拆解类文章的价值在调查深度：作者替读者读了源码、翻了 PR、跑了实验。

## 结构

整篇围绕一条问题链展开，每个章节回答一个问题，前一章的结论引出下一章的问题，读完第 3 节就想知道第 4 节。开头三段内交代清楚：遇到了什么问题或现象、这篇文章最大的发现、读完能知道什么。

## 每个章节怎么写

先抛出具体问题，再展示一手证据，然后用自己的话说明这对读者意味着什么。

- 一手证据包括源码片段（标注文件路径和行号）、官方文档或博客原文、自己跑出来的实测数据、GitHub issue 和 PR 讨论原文
- 代码片段只截和观点直接相关的部分（5 到 15 行），代码前一句说它在做什么，代码后一句说它意味着什么
- 把代码逻辑翻译成读者能操作的结论，比如“清单里只注入 description，description 没写好，模型就不知道这个 skill 存在”
- 章节之间的节奏可以变化，有的章节以源码为主，有的以实测数据为主

## 调查方法

1. clone 或打开目标项目源码，按文章主题 grep 关键词、看目录结构，定位关键文件
2. 找到支撑观点的常量定义、核心逻辑和注释
3. 只保留满足以下条件之一的代码片段：把一个模糊的说法量化了（“限制为 250 字符”）、暴露了一个设计取舍、和常见的理解对不上并且有证据
4. 先有代码再有结论。如果不贴代码结论也不会变，这段代码就只是装饰，不要贴

## 常见失败

- 贴了大段代码，只说一句“可以看到实现了 X 功能”，读者不知道和自己有什么关系
- 章节之间各自独立，像百科词条合集
- 用“据说”“业内普遍认为”支撑核心论点
