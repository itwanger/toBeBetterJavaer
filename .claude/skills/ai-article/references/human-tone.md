# 二哥的统一表达标准（口播稿与技术文章共用）

## 1. 正向表达规范

口播稿与技术文章共用一套“短句主谓宾 + 准确技术概念 + 通俗因果推导”的干练表达：

- **主语直接用产品名或组件名**：直接写“翻开 Claude Code 的源码能看到”“DeepSeek Harness 会先做一步轻量裁剪”。
- **Agent 产品定位认知**：Claude Code、DeepSeek Harness、Codex 都统称为 Agent。它们既能在终端运行，也能在桌面端运行；除了写代码，还能写教程、做 PPT、做视频、处理文档和完成各类日常工作。行文和口播举例时不要把使用场景局限于“程序员写代码”。
- **名词平实准确，技术状态直陈事实**：使用平实的核心名词（如“终端”“第一条消息”“追加一条新消息”“规则”“达到上下文窗口的阈值”“缓存未过期/缓存过期”“消息内容一变”“通知服务端删除”），不加多余的修饰前缀，不打生硬比喻，不字面直译英文注释。
- **动词干脆直接，一步到位**：用直白的动作词串起执行流程（如“挂载、暴露、读取、折叠、设定、挂起、放行、切换、跑、切到、查、塞进、裁掉、剔掉”），讲完动作本身即止。
- **只用约定俗成的公共术语，把底层机制转化为通俗因果逻辑**：只保留读者有概念的行业公共术语（如 `KV Cache`、`Prefix Caching`、`Prefill`、`TTL`、`tool_result`、Sub-agent、Multi-Agent、MCP）以及有直观体感的代表性数字（如 `50` 轮、窗口容量的 `80%`、`5` 分钟、`1` 个小时）。源码内部实现全部转化为“日常痛点是什么 → 怎么处理的 → 哪部分受益、哪部分付出什么代价”的白话描述。
- **技术边界严密，因果不跳步**：讲清哪一段命中、从哪个位置开始断开重算，以及方案付出的额外代价（如“被裁剪的那条消息之前的前缀没变，还能继续命中缓存，从裁剪位置往后的部分则需要重新 Prefill”）；从动作到结果之间，用半句大白话把原理搭上桥（如“消息内容一变，提示词缓存是按前缀匹配的，从被改的那条消息开始，后面的缓存就都对不上了，等于白白重算一遍”）。
- **问句短促直接，选项精炼**：只问核心问题（控制在 20 字以内），把触发条件和实现细节留给正文回答；A/B/C 保持三个短选项，多路径答案拆成两个选项做成 `B + C` 多选。
- **数字与单位贴合日常读写**：容量写 `8 M`、`16 G`，状态分值写 `0`、`1`。

## 2. 自动化用词检查

生造词、翻译腔与冗余修饰词表统一维护在 `scripts/wording_rules.py` 中，交稿前通过脚本自动拦截，不在正向规范中罗列负向词例。
