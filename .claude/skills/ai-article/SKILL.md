# AI 技术文章写作

## 第一原则（最高优先级）

我在读你交付的内容时，必须感知到是一个活生生的人。这个人知道一些事，也有不知道的。他讲细节，敢下判断，愿意交付有深度的内容。

"活人感"不是靠口头禅、网络梗装出来的。首先手上有真实的东西（事实、数据、经历），其次能说清楚自己为什么知道这件事，最后才是语气。

用下面这个对比检验写法：

> 他毕业后离开上海，去了成都。那套量化程序已经跑过一段时间，他觉得可以全职试试。收入会不会稳定，当时没人知道。

这比"他关掉一条好走的路，把命运押上赌桌"更接近目标。前一种写法告诉读者他做了什么、条件是什么、风险在哪里。后一种什么具体信息都没给，只是在摆造型。

## 写作优先级（遇到冲突按此排序）

1. **读者能学到东西** — 有信息差、技术准确、读完有收获
2. **少即是多** — 写完砍掉三分之一，没有信息损失就说明原来是水分。一个技术方案挑最关键的一两个数字讲透，其余带过
3. **读完觉得作者是个真人** — 有判断、有情绪、有经验
4. **格式规范** — 满足下面的格式规则

## 格式规则

- 正文标题：`## 01、标题`，标题只写名称
- 段落要短。一个段落不能超过两个句号，超了就拆
- 用"大家/我们/小伙伴"和读者拉近关系，少用"你"
- 项目自定义类名用通俗功能描述代替（"循环预算机制"而非 `AgentBudget`）
- 英文术语首次出现加中文翻译，MCP、RAG、LLM 等约定俗成的缩写直接用
- 数字必须有出处（源码、文档、实测），没出处用模糊表达（"大部分""差不多"）
- 模型举例用最新的（Opus 5、GPT-5.6、GLM-5.2）

## 怎么写好

**技术内容要准确。** 承载技术信息的句子用词要准确无歧义。技术陈述和个人判断分开写，先说事实再给观点。

**情感表达要自然。** 不承载技术信息的句子用自然口语。自嘲、预判读者反驳、情绪直给都欢迎，但不要硬造。

**一句话能说清楚的事不要两句。** 同义反复的过渡句（"说完了 A，接下来看看 B"）直接删。

**去 AI 味的方法：默读。** 写完每一段默读一遍，问自己"转发给朋友，朋友会不会觉得这是 AI 写的？"觉得别扭就改。AI 味的特征见 `references/human-tone.md`。

## 前言写法

前言是一篇独立的短文，读者只看前言就应该觉得"这个作者有东西"。默认 ~800 字。

三个要素：钩子（热点事件或反差冲突）、声明（为这篇文章做了什么）、姿态（带读者一起学习的人）。

核心立场：作者是读者的同路人，引导读者学新东西的动机是"在稳定的状态下变得更好"。

**前言要从 sucai.md 的素材里长出来，不要另起炉灶套公式。**

## 特色元素

### 简历包装

文章涉及实战项目时加一段：项目名称、项目简介、技术栈、核心职责（5 条）。

#### PaiCLI如何写到简历上？

项目名称：CodeMate——Agent CLI 编程助手 2026.03 – 2026.05

项目简介：面向 Java 项目的本地 CLI 编程 Agent，支持自然语言驱动代码检索、任务规划、代码修改及自动诊断，集成 Multi-Agent、代码检索、长期记忆及安全执行能力，实现从需求分析到代码交付的自动化开发流程。

技术栈：Java 21、JLine、JavaParser、SQLite、JGit、Ollama、Jieba

核心职责：

- 设计 ReAct 与 Plan-Execute 双模式执行框架，简单任务采用 ReAct 完成工具调用与迭代推理，复杂任务拆分为 DAG 并由调度器按依赖关系并行执行；结合 Planner、Worker、Reviewer 多 Agent 协作，根据审查结果自动修复失败节点并控制重试次数，提高复杂开发任务执行成功率。
- 构建代码仓库检索能力，优先通过 ripgrep 快速定位代码，再结合 JavaParser 按类、方法生成 AST 索引，并融合 Ollama Embedding、Jieba、BM25 等方式完成语义检索与关键词检索，实现跨文件代码定位；在千级代码块规模下检索 P90 延迟保持在 94ms。
- 设计短期、长期双层记忆机制，将对话、工具结果及任务状态分别管理，并采用 Map-Reduce 对历史上下文进行摘要压缩；长期记忆基于 SQLite 持久化，结合 BM25 与向量检索动态召回相关历史，提高跨会话代码开发连续性。
- 基于 Git Worktree 为每个任务创建独立工作区，并结合 Side-Git 保存执行过程中的代码快照；通过 Diff 与 Java LSP 自动收集代码修改及诊断结果反馈给 Agent，在保证任务隔离的同时支持失败恢复与增量修复。
- 建立 Java Code Agent 自动评测体系，基于 SWE-bench Multilingual 与 Harbor 构建 43 个真实开源 Issue 测试集，在固定代码版本及隔离环境下自动验证 Patch，成功修复 27 个任务，Pass@1 达到 62.8%。

### 截图占位符

每个章节至少 1 个占位符，超过 500 字安排 2 个。格式：

```
【截图：<名称>；风格：<风格>；截图目标：<证明什么>；关键词：<关键词1>、<关键词2>、<关键词3>】
```

风格只选 6 种：`whiteboard`（架构图）、`skill-card`（技能卡片）、`data-board`（数据对比）、`three-layer`（层级关系）、`swimlane`（泳道流程）、`checklist-card`（注意事项）。

## 工作流程

### 步骤 1：读素材 + 选题质检

精读 `./sucai.md`，提取关键信息。用 IKR 评估：有信息差吗？读者能学到什么？能戳中什么情绪？

### 步骤 2：调查

项目相关内容必须先调查再写。

| 文章类型 | 最低调查深度 |
|---------|------------|
| 安装教程类 | 表层：官方博客、文档、公开榜单 |
| 产品评测类 | 中层：GitHub README、issue、PR、commit 历史 |
| 面试八股类 | 深层：读源码，找到具体实现 |

**知识库优先**：先检查 `./knowledge/` 下有无缓存调研文件。源码调研交给 Sub-agent 做，不在主对话里读源码。

**源码只是参考**：源码实现如果设计粗糙，答案按业界最佳实践写。大纲里标注哪些基于源码、哪些按理想方案写。

### 步骤 3：搜集公开信息

补充可引用的公开数据。数据必须从原始来源获取。

### 步骤 4：选择风格

用 `AskUserQuestion` 让用户三选一：安装教程类、产品评测类（见 `references/review-style.md`）、面试八股类（见 `references/interview-style.md`）。

### 步骤 5：出大纲（用户确认后再写）

根据 `sucai.md` 输出大纲：结构骨架、源码参考策略、前言样本（~800 字）。用户确认后再写。

### 步骤 6：撰写

写之前看一遍 `references/human-tone.md` 找语感。扫一眼 `inbox.md` 看有没有能用的素材。

文件格式为 Markdown。面试篇每道题的目标：回答清楚，让面试官认可。

头部模板：
```yaml
---
title: # 写完后回填
shortTitle: # 写完后回填
description: # 50-120 字 SEO 描述
keywords: # 5 个搜索关键词
tag:
  - Agent  # 面试对话类用：- 面试
category:
  - AI
author: 沉默王二
date: # YYYY-MM-DD
---
```

写之前通读对应风格的参考文件。

### 步骤 7：自检

**机械检查**：
- `./scripts/check_body_length.py` 检查字数 ≥ 4000
- `python3 ./scripts/check_prose.py <稿件路径>` 检查翻案腔、破折号等
- 逐段数句号，超过 2 个的拆成短句
- grep `references/human-tone.md` 禁用词速查表

**通读检查**：假装第一次看这个话题，默读全文一遍。哪里像 AI 写的就改，哪里想跳过就是水分，哪里删掉读者也不少知道什么就是废话。

自检完成后给用户简短报告。

### 步骤 8：落盘

保存到 `docs/src/sidebar/itwanger/ai/`，同时存草稿到 `./drafts/`。保存后整理截图来源链接清单。

### 步骤 9：复盘沉淀

用户说"复盘""对比"时执行。读正式稿和草稿 diff，归类改动，提炼可复用的规则写回 Skill 文件。消化 inbox，清理草稿。

**复盘时注意：新规则要正向表述（"怎么写好"），不要只加禁止性规则（"别犯错"）。规则总量只减不增，新规则进来就要合并或删掉旧的。**
