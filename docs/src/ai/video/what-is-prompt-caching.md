## 提示词缓存到底是什么

先说第一件事，提示词缓存到底是什么。

很多人以为提示词缓存，是把模型之前生成过的回答直接存下来。

其实完全不是。

大模型最烧钱、最耗时的步骤叫预填充。它要把你发过去的全部提示词做一轮庞大的矩阵乘法，算出注意力机制需要的矩阵数据，也就是 KV Cache。

这就好比开了一家高档牛肉火锅店。你的系统指令、工具定义和长文档资料，就像后厨慢火熬了三个小时的牛骨高汤；用户这次新提的问题，不过是端上桌涮十秒钟的一盘鲜牛肉。

没有提示词缓存的时候，每来一个客人点一盘牛肉，后厨非得把整锅高汤倒掉，重新熬三个小时。客人等得直拍桌子，老板的燃气账单也得当场破产。

提示词缓存干的事，就是把熬好的高汤一直热在锅里。只要新请求的前缀和上次一模一样，模型直接复用算好的 KV Cache，跳过预填充，首字响应秒出，费用自然能直接打一折。

## 为什么你的提示词永远命中不了缓存

那聪明的你肯定想到了：既然只要前缀一样就能命中，为什么很多人自己写应用，缓存命中率几乎是零？

一句话点破真相：前缀被你自己亲手毒死了。

【截图：前缀断裂与缓存失效示意图；风格：swimlane；截图目标：展示因为在开头动态插入时间戳导致整条前缀缓存全部击穿的处理流程；关键词：前缀匹配、时间戳污染、缓存失效、Token 对齐】

大模型缓存认的是从第一个字符开始的绝对匹配。开头的字符一旦变了，整条哈希链彻底断裂，后面哪怕跟着上万字完全相同的文档，也会全盘失效。

很多新手写提示词有个坏习惯，喜欢在系统指令第一行加上当前时间戳，比如几点几分几秒，或者塞进一个动态生成的请求编号。在模型眼里，开头的字符每秒都在变，后面的静态内容就全部变成了缓存未命中，白白浪费巨额算力。

另外，每次序列化工具定义时字典键名随机乱跳，或者前后端拼接文本时手抖多敲了一个空格或换行，都会让精心设计的缓存瞬间击穿。

## 怎样才能做好提示词缓存

那聪明的你肯定又要问了：怎样才能把提示词缓存做好，真正省到钱？

核心法则只有八个字：静态在前，动态在后。

【截图：提示词金字塔编排规范；风格：checklist-card；截图目标：展示静态前缀前置、动态后缀后置的四层物理排布规范；关键词：静态前缀、动态后缀、金字塔结构、追加原则】

提示词必须按金字塔结构排布。最顶层放绝对不变的全局设定、工具定义和示范问答，这部分在所有请求间都可以百分之百复用；第二层放多轮对话共享的参考材料、代码库上下文或者知识库文档，在会话中持续命中；至于用户当轮提的具体问题、动态时间戳和临时变量，必须老老实实挪到提示词的物理最末端。

在编写 Agent 或者多轮对话时，还要守住追加原则。工具调用的参数与返回结果，一律按顺序往后追加，绝不要为了自以为是的省空间而去篡改中间的历史消息。只要保证前面的长前缀坚如磐石，哪怕交互几十轮，你也能稳稳享受毫秒级响应和骨折级底价。
