title: Agent 什么时候该等你点头再动手？
---

面试官问你：“Human-in-the-loop 怎么设计？”如果你回答“危险操作之前弹一个窗，让用户确认一下就行”，恭喜你，出门右拐回家等通知吧。

为什么？

因为弹窗弹多了，人就不看了。Anthropic 在 2026 年 3 月发布的 auto mode 工程博客里提到，Claude Code 的用户批准了 93% 的权限请求。Anthropic 把这种现象叫作审批疲劳，人点得越多，越不在意自己批准的到底是什么。

【截图：审批疲劳；风格：data-board；截图目标：展示 Claude Code 用户批准 93% 权限请求的数据，以及人点多了不看内容直接点“允许”的现象；关键词：93%、审批疲劳、Yes】

Human-in-the-loop，中文叫人在回路中，就是在 Agent 的执行过程中设置一些需要人来做决定的节点，人批准、修改或者拒绝以后，Agent 再接着执行。难点不在弹窗本身，而在于哪里该弹，哪里不该弹。

恭喜看到这里的你，已经成功击败 30% 的学习者，给自己鼓个掌吧。**接下来我问你，哪些操作必须等人点头？**

A，所有写操作；B，除了只读操作以外的全部操作；C，按风险和可逆性分级。聪明的你可以把答案打在弹幕或者留言区。

我的答案是 C。

只读操作，比如读取文件、搜索代码，直接执行。可回滚的写操作，事后通知就行，比如 Claude Code 的 auto mode，对项目目录里的文件编辑直接放行，改错了用 Git 就能撤回。不可逆的操作，以及涉及资金、权限、对外发送的操作，比如删除数据库、转账、群发邮件，必须事前审批。

审批的内容也要具体。只问一句“是否继续”，人根本没法判断。要把完整的命令、要修改的文件 diff、订单的金额摆出来，人看一眼就知道自己批准的是什么。

【截图：按风险和可逆性分级；风格：three-layer；截图目标：三层分别是只读操作自动执行、可回滚写操作事后通知、不可逆操作事前审批，每层配一个例子；关键词：只读、可回滚、不可逆】

一句话概括，撤得回的事后告诉你，撤不回的事前问你。恭喜你，已经成功击败 50% 的学习者了。

**接下来继续问你，怎么才能少打扰人？**

A，记住授权；B，把规则写在前面；C，交给另一个模型审查。聪明的你会选哪一个？

我的答案是三个都要。

先说记住授权。Claude Code 的审批弹窗里有一个选项叫“Yes, and don't ask again”，选了它，Bash 命令的授权会写进仓库根目录的 .claude/settings.local.json，下次遇到同样的命令就不再询问；文件修改的授权则只在当前会话里有效。

再说规则。Claude Code 的权限规则分 deny、ask、allow 三种，按 deny、ask、allow 的顺序匹配，先匹配上哪一条就按哪一条执行。allow 规则没法给 deny 规则开例外，所以把 rm -rf 这类命令写进 deny，任何时候都执行不了。

最后是交给另一个模型审查，这就是 auto mode 的做法。规则判断不了的操作，比如 Shell 命令、网络请求、项目目录以外的文件操作，交给一个分类器模型审查。分类器分两个阶段，第一个阶段只输出一个 Token，判断要不要拦截，被标记了，才进入第二个阶段做推理。按照 Anthropic 那篇博客的数据，误报率从 8.5% 降到了 0.4%。

这里有一个细节，分类器只看用户的消息和 Agent 的工具调用，不看工具返回的结果。因为网页和文件里藏着的恶意指令，都是从工具结果进入上下文的，这就是提示词注入。被拦截的操作会作为工具结果返回给模型，让模型换一种更安全的做法；连续被拒绝 3 次，或者累计被拒绝 20 次，Agent 就停下来，交给人处理。

【截图：auto mode 三层放行；风格：swimlane；截图目标：第一层内置白名单和用户规则，第二层项目目录内文件操作，第三层分类器两阶段审查，被拒后返回模型，连续 3 次或累计 20 次交给人；关键词：allowlist、classifier、20 次】

恭喜你，成功击败 70% 的学习者了。

**继续问你，等人点头的时候，Agent 怎么停下来？**

A，在循环里 sleep，等人回复；B，保存状态后退出，人回复以后再恢复；C，让模型自己再问一遍。

我的答案是 B。审批可能要等几分钟，也可能要等到第二天，进程一直挂着等，服务一重启，任务就没了。

OpenAI Agents SDK 的做法是，给工具设置 needs_approval，模型调用这个工具时，运行就会暂停，结果里的 interruptions 列出待审批的工具调用。调用 to_state 方法转成 RunState，再用 to_json 方法存进数据库。人批准以后取出来，调用 approve 或者 reject，再交给 Runner 接着执行。

LangGraph 用的是 interrupt 函数，调用时把整张图的状态存进 checkpointer，也就是状态存档器，人回复以后，用 Command 带上 resume 的值恢复执行。

这里有一个坑。LangGraph 恢复时，不是从 interrupt 那一行接着执行，而是把整个节点从头执行一遍。如果你在 interrupt 之前就扣了款，恢复以后就会再扣一次。所以 interrupt 之前的操作必须幂等，也就是重复执行多次，结果和执行一次一样。

【截图：挂起与恢复；风格：whiteboard；截图目标：Agent 遇到审批点暂停，状态存进数据库，人批准或拒绝后取出状态恢复执行，标注 LangGraph 节点从头重跑的坑；关键词：needs_approval、RunState、interrupt】

当然，人也要能随时按下停止，不必等到审批点。恭喜你，成功击败 90% 的学习者了。

最后，面试官如果追问：“全自动的场景，没人审批，怎么办？”

告诉他，用边界代替审批。Pi 这个 Agent 默认不做权限审批，它的安全文档里写得很直接，盯着对话记录、审查改动，都不构成安全边界，真正的安全来自限制 Agent 能访问的文件、凭证、进程和网络，推荐把 Pi 放进容器或者微型虚拟机里运行。确实需要审批，就装上 permission-gate 扩展，在 rm -rf、sudo 这类命令执行之前弹窗确认，没有界面的时候直接拦截。Codex 跑在 CI 里，就把 approval_policy 设为 never，再配合沙箱限制读写和网络。

沙箱限定 Agent 能碰到什么，白名单决定哪些操作不用问，事后审计把每一步操作记下来，出了问题能查清楚。

恭喜你升到王者段位了，成功击败 99% 的学习者。

最后简单总结下。

撤不回的操作等人点头，撤得回的操作交给规则和沙箱。

另外，建议你打开项目里的 .claude/settings.local.json 看一看，平时随手点“don't ask again”攒下了哪些 allow 规则，把范围太宽的删掉。
