## 01、泛 Coding 的四个Case

先看 GLM-5.4 这一代的规格升级。

它接入了一个 `24` 层的视觉编码器，终于有了原生的视觉理解能力，支持视频、图像、文本和文件四种输入，上下文窗口提升到 `1M`，单次最大输出 `128K`。

智谱借着这次发布提出了一个新方向，叫泛 Coding。意思是代码不再只用来写前端和后端，还能作为基础工具，去驱动视频、3D 渲染、游戏和机械设计这类跨领域任务。

![](https://cdn.paicoding.com/stutymore/glm-5-4-review-02-specs-20261124102708-e43513a5.png)

### 自述 MV

第一个案例是 GLM-5.4 的自述 MV《Hello world》，创作者 Mike Luan 借助 GLM-5.4，完成了从创意、编曲、动态编排到画面渲染的全部流程。

![](https://cdn.paicoding.com/stutymore/glm-5-4-review-03-hello-world-20261124102708-4ca2a59b.gif)

有意思的地方在于，整支 MV 的画面没有用任何现成的图片素材，全部靠前端代码实时绘制出来。背景音乐则由 GLM-5.4 按章节和镜头做规划，调用外部的音乐生成模型来生成，再由它自己完成多轮提示词修改。

### 3D 观鸟

第二个案例偏图形学，很考验基本功。创作者“夜神不说话”让 GLM-5.4 在不使用任何外部 3D 模型和贴图的前提下，从零写出了一个可交互的 3D 观鸟。

![](https://cdn.paicoding.com/stutymore/glm-5-4-review-04-bird-20261124102708-33d93843.gif)

画面里的主角是一只长尾山雀，羽毛、呼吸时的起伏、歪头的动作和眨眼时的动作，全都由数学加上自定义的 GLSL 着色器计算出来。

### FreeCAD 机械臂

第三个案例是工业机械设计。GLM-5.4 先通过代码驱动 FreeCAD 完成机械臂的 CAD 建模，接着调用 Blender 编排机械臂抓取 Logo 的运动轨迹，再做材质渲染并合成音频。

![](https://cdn.paicoding.com/stutymore/glm-5-4-review-05-robot-arm-20261124102713-e369e03b.gif)

### 完整游戏

第四个案例是完整的游戏开发。GLM-5.4 用代码一次性完成了角色移动、物理碰撞、地图搭建、战斗系统和美术资产，交付了一个能运行的完整游戏原型。

![](https://cdn.paicoding.com/stutymore/glm-5-4-review-06-game-20261124102715-4f0039c8.gif)

### 跑分

对比上一代 GLM-5.3，GLM-5.4 超过一半的场景比上一代完成得更好。

## 03、雷霆大思考

前面测《精灵小镇》第一轮时，开着最高档位，光思考就花了将近 `20` 分钟。这恰好是 GLM-5.4 最受关注的一个特点，官方还专门发帖提醒过大家。

Z.ai 负责人 LiZixuan 在某知名社区平台也提醒了，说 GLM-5.4 很容易进入“雷霆大思考”模式。

![](https://cdn.paicoding.com/stutymore/glm-5-4-review-12-thinking-20261124102719-8faefab1.png)

在排查疑难 Bug、阅读大型代码仓库或者补全套测试用例时，这种自我反思和纠错能提高准确率。

**那有没有办法简单任务自动切换到 GLM-5.3-Flash 模式呢？**

我把 ZCode 4.0.0 的官方文档从头到尾翻了一遍。

没找到类似 Antigravity Orchestrator 那样的路由开关，没法在同一个输入框里按任务难度自动切换主模型，想切换主会话的模型，仍然需要在对话框里手动选择。好消息是，ZCode 已经提供了两套现成的机制，组合起来可以把“Flash 跑腿、5.4 攻坚”做成自动化或半自动化的工作流。

![](https://cdn.paicoding.com/stutymore/glm-5-4-review-13-routing-20261124102721-a5afef7f.png)

### 子智能体加规则自动分流

这是目前在 ZCode 里最接近全自动化的一套方案。

打开 ZCode 的设置页面，进入子智能体管理，每个子智能体都能单独指定模型和推理强度。系统会自动把配置保存为 `~/.zcode/agents/<name>.md`（用户级，全局生效）或 `<项目>/.zcode/agents/<name>.md`（仅对单个项目生效）。

根据工作习惯的不同，可以有两种配法。

第一种是省 Token 的配法。主会话用 GLM-5.3-Flash 处理小活，再新建一个 GLM-5.4 最高档的专家子智能体，写清楚触发条件。小改动由主会话直接快速完成，架构和疑难 Bug 自动派给专家子智能体，也可以用 `@deep-engineer` 直接点名。

第二种是重度开发的配法。主会话用 GLM-5.4，把内置的只读检索子智能体 `Explore` 和处理常规任务的 `general-purpose` 改成 GLM-5.3-Flash。查代码、翻目录这些事交给 Flash，不让 GLM-5.4 把雷霆大思考浪费在找文件上。

如果你想用省 Token 的配法，可以在 `~/.zcode/agents/deep-engineer.md` 写入下面这份配置，新建会话或发送 `/reload` 就能生效：

```markdown
---
name: deep-engineer
description: 处理跨模块架构设计、疑难 Bug 深度排查、核心重构以及完整测试套件编写等高复杂度工程任务
model: glm-5.4
thoughtLevel: max
injectAgentsMd: true
---

你负责处理主会话转交的高难度工程任务。动手修改前先梳理清楚调用链与边界条件，给出验证命令并确保测试通过，完成后向主会话返回清晰的改动摘要。
```

再往全局指令文件 `~/.zcode/AGENTS.md` 里补一条分流约定，写明遇到跨文件重构、疑难排错或编写完整测试时，优先委派给 `deep-engineer`，日常的小改动和快速查询留在主会话里完成。

![](https://cdn.paicoding.com/stutymore/glm-5-4-review-14-delegation-20261124102721-be5f0470.png)

### 动态工作流混合调度

如果你要跑全库审计、批量迁移、深度调研这类需要大量并发的任务，ZCode 官方推荐用动态工作流来调度两个模型。

在设置里的行为与工具页面，把动态工作流设为始终开启（也可以在输入框里手动输入 `/workflow`），ZCode Agent 会先写一段编排脚本，调度多个子智能体分阶段并行执行，最后回到主对话汇总结果。

ZCode 官方文档在介绍子智能体模型时，给的示例就是“工作流子智能体使用 GLM-5.3-Flash”。也就是说，主对话里的 GLM-5.4 负责拆分阶段、制定规范和最终把关，并发执行的子智能体全部交给 GLM-5.3-Flash。跑通之后，点击完成卡片上的保存按钮，还能存成 `.dwf.ts` 模板，一键复用。

![](https://cdn.paicoding.com/stutymore/glm-5-4-review-15-workflow-20261124102722-e942cbe1.png)

## 04、Loop Transformer

GLM-5.4 并没有靠堆参数量来换效果，底座依然是 `750B` 级别的 GLM-5 模型，但智谱称它的智能水平相当于 `2T` 到 `3T` 参数级别的模型。

靠的就是 Loop Transformer 架构。

按照智谱技术博客的说法，记忆型任务能从更大的参数规模中受益，而大型软件工程、网络安全、3D 建模这类任务，需要的是更多的计算深度。

![](https://cdn.paicoding.com/stutymore/glm-5-4-review-16-loop-20261124102723-40290128.png)

传统的 Transformer 在一次前向计算里，每一层只执行一遍。Loop Transformer 则是挑出中间一组共享权重的网络层，让它们连续跑多轮，每一轮都基于上一轮算出来的中间状态继续计算。

这个思路早在 2018 年的 Universal Transformer 论文里就提出过，但以前效果不好。

智谱这次换了一种做法，在已经预训练好的 `750B` 级 GLM-5 基座上继续训练，把它改造成 Loop Transformer。从官方架构图可以看到，整个底座共 `78` 层，前 `26` 层做前置处理，中间第 `27` 到 `54` 层这 `28` 层跑两轮循环，最后 `24` 层负责收尾。

算下来，参数量几乎没有增加，模型单次前向推理的等效深度却从 `78` 层提升到了 `106` 层。

不过，要把循环结构放进 `750B` 规模、`1M` 上下文的模型里，处理不好很容易出现训练不稳定的问题。智谱在博客里公开了三项关键的工程改动。

### 门控渐进更新

GLM-5.4 为每一轮循环加上了独立的逐 Token 门控，按比例把候选写回残差流。

![](https://cdn.paicoding.com/stutymore/glm-5-4-review-17-gates-20261124102726-25db5108.png)

训练稳定之后，两轮循环形成了清晰的分工。第一轮的门控值普遍偏小，以较小的步长建立全局上下文，稳定数值分布；第二轮的门控值更大，在第一轮状态的基础上进一步精炼结果并写回。遇到更难预测的 Token 时，第一轮的门控值也会自动变大，让这些复杂位置更早进入深度计算。

### KV Cache 全局共享

在 `1M` 长上下文中，如果每循环一轮就单独存一整份 KV Cache，显存占用会随循环次数成倍增加，线上部署根本扛不住。

![](https://cdn.paicoding.com/stutymore/glm-5-4-review-18-cache-20261124102727-3c5c7f45.png)

GLM-5.4 采用了全局共享加独立滑动窗口的混合方案。第二轮循环不再重新缓存整段长文本的键值，而是复用第一轮选出来的稀疏 KV，只额外保留一个长度为 `128` Token 的局部滑动窗口，用来存放第二轮新更新的近距离信息。

这两部分信息在计算注意力时会合并到同一次运算里，既能看到第一轮的全局上下文，也能用上第二轮更新后的局部表示。这样一来，多跑一轮循环，显存只多占一个小窗口，在 `1M` 长度下也把部署成本的增幅控制住了。

### 复用稀疏注意力索引

第三个改动针对的是检索耗时。GLM-5.4 的底座采用稀疏注意力，第二轮循环跳过了重新计算注意力索引器的步骤，直接复用第一轮算出来的 `top-k` 索引（`k = 2048`），检索开销没有增加，官方实验显示，效果和每轮重新计算几乎一样。

除了这几项结构优化节省下来的显存和算力，团队还在推理框架层做了核心算子融合，减少中间结果在显存里的反复读写，最终让循环架构跑出了高峰时段 `70–80 token/s`、非高峰时段最高 `200 token/s` 的吞吐。

![](https://cdn.paicoding.com/stutymore/glm-5-4-review-19-ablation-20261124102727-e52508b6.png)

简单来说，Loop 架构把一部分原本要靠拉长思维链来完成的推理，放进了网络层内部的循环里。
