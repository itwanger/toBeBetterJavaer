## content

### 01、介绍一下自己的项目，整体架构和技术栈是什么？

“做了两个项目，一个终端 Agent，一个 RAG 知识库。”

【截图：两个项目架构总览；风格：three-layer；截图目标：展示 PaiCLI 和派聪明的整体架构关系；关键词：PaiCLI、派聪明、架构】

“终端 Agent 叫 PaiCLI，对标 Claude Code。其中 ReAct 模式用于实时交互的短任务，Plan-and-Execute 模式用于需要分步规划的复杂任务，Multi-Agent Team 模式用于多角色协作。”

“RAG 知识库叫派聪明，基于 Elasticsearch 做混合检索。向量检索用 KNN，关键词检索用 BM25，两个结合起来做召回和排序。上层用了自定义的 ReAct 来支持工具调用和多轮对话。”

“技术栈层面，PaiCLI 是 Java 21 + OkHttp + SQLite + JLine，非常原生，没有用 Spring AI 这些框架。派聪明是 Spring Boot + Elasticsearch 8.x + Embedding/LLM API + Redis。”

#### PaiCLI 为什么设计三个模式？

“因为不同的任务需要不同的模式来适配。”

【截图：三条路径适用场景对比；风格：data-board；截图目标：对比三种模式的适用场景和开销；关键词：ReAct、Plan、Team】

“举个例子，用户问‘这个方法是干什么用的’，ReAct 模式就搞定了。但如果用户的指令是‘帮我重构这个模块，改完测试一下’，ReAct 就不够用了，需要用Plan-and-Execute 先拆解任务、编排依赖、然后再分步执行。更复杂的场景，比如需要多 Agent 协作，就可以上 Team 模式。”

### 02、项目中 Agent 的完整流程是怎样的？

“以 ReAct 模式为例，走一遍完整流程。”

【截图：ReAct 完整执行流程；风格：swimlane；截图目标：展示从用户输入到最终响应的完整数据流；关键词：ReAct、LLM、工具调用】

“用户输入进来后，第一步做输入预处理，本地路径展开、图片引用解析。第二步检索长期记忆，把和当前输入相关的记忆条目注入系统提示词。第三步组装 Prompt，分层拼接，静态层在前动态层在后。”

“然后进入主循环。每轮先检查退出条件，token 预算是否耗尽、有没有出现停滞（连续多次调用同样的工具）、是否超过迭代上限。检查通过后调用 LLM，如果返回了工具调用请求，就执行工具。多个工具可以并行，有超时兜底。工具结果作为消息追加到对话历史，LLM 继续决策。”

“如果 LLM 没有返回工具调用，说明任务完成，格式化输出返回给用户。”

#### 审批机制怎么设计的？

【截图：审批流程决策树；风格：swimlane；截图目标：展示写操作的审批流程；关键词：审批、路径检查、命令检查】

“写操作要过审批。write_file、execute_command 这些工具在执行前会走 HITL（Human-in-the-Loop，人机协作）审批流程。路径检查器判断文件路径是否在允许范围内，命令检查器判断命令是否安全。审批策略分三档：auto（自动通过）、suggest（建议确认）、never（必须手动确认）。”

“读操作不需要审批，直接执行。”

### 03、项目过程中针对 Agent 做过哪些优化？具体怎么调优？

“三个方向：省钱、防溢出、防死循环。”

“省钱靠 Prompt Caching。PaiCLI 的 Prompt 一共 9 层，前四层是静态的，身份定义、人格、模式指令、审批策略，整个会话期间不变。把这些静态内容排在最前面，Prompt Caching 按最长公共前缀命中，前缀越稳定，缓存命中率越高。”

【截图：Prompt Caching 命中策略；风格：three-layer；截图目标：展示静态层前置如何提高缓存命中率；关键词：Prompt Caching、静态层、前缀】

“防溢出靠两层压缩。第一层是短期记忆压缩，token 数超过预算时，自动淘汰最旧的条目。第二层是对话历史压缩，当对话历史的 token 数逼近上下文窗口上限时，保留最近几轮完整对话，把更早的历史用 LLM 生成摘要替换掉。”

“防死循环靠 stagnation（停滞）检测。每次工具调用记录签名（工具名 + 参数），如果连续 3 次签名完全一样，判定为停滞，强制退出循环。”

#### 压缩触发阈值怎么算的？

【截图：压缩触发阈值计算；风格：data-board；截图目标：展示不同窗口大小下的触发阈值；关键词：压缩触发、200K、阈值】

“公式是：触发阈值 = 上下文窗口 - min(20K, 窗口/4) - min(13K, 窗口/8)。”

“200K 窗口算下来大约 167K 触发，1M 窗口大约 967K 触发。预留的空间用来放摘要内容和后续对话，不会压缩完马上又溢出。”

### 04、Agent 优化有哪些常见手段？

“成本、质量、速度三个方向，每个方向有一个优先级最高的事。”

“成本方向，Prompt Caching 投入产出比最高。Agent 的系统提示词通常很长，工具定义、项目规则、记忆注入加起来好几万 token，而且每轮对话都要完整发一遍。Prompt Caching 的原理是按前缀匹配，你发给模型的 Prompt，前半段和上一次请求相同的部分直接走缓存，不重新计算，计费只收大约十分之一。PaiCLI 把 9 层 Prompt 里前 4 层静态内容排在最前面，整个会话期间一个字不变，缓存命中率就高。”

【截图：Prompt Caching 前缀匹配原理；风格：three-layer；截图目标：展示静态层前置如何提高缓存命中率；关键词：Prompt Caching、前缀匹配、静态层】

“其次是模型分级。意图识别——判断用户这句话是要读文件还是跑命令——用小模型就行，速度快、成本低。复杂推理比如任务规划和代码生成才调大模型。再就是上下文裁剪，按优先级砍掉对话历史的早期部分，用摘要替代。”

“质量方向，提示词分层管理最重要。系统提示词拆成独立的层，每层管一件事。改语气风格只动人格层，加审批策略只改审批层，改动范围可控，不会一改全炸。配合评测驱动迭代，改 Prompt 之前跑一轮评测记基线，改完再跑一轮对比，数据说了算。”

【截图：Prompt 分层管理示意；风格：three-layer；截图目标：展示 9 层 Prompt 各自职责和修改影响范围；关键词：分层管理、隔离修改、评测驱动】

“速度方向，工具并行带来的体感提升最大。Agent 一轮经常要调多个工具，比如同时读 3 个文件。PaiCLI 用线程池最多 4 个工具同时执行，总超时 90 秒。加上流式输出，用户不用等全部生成完才看到内容。”

#### 为什么 Prompt Caching 排在成本优化的第一位？

【截图：Prompt Caching 成本对比；风格：data-board；截图目标：对比有无缓存时 20 轮会话的 token 计费差异；关键词：缓存命中、计费、成本节省】

“系统提示词是 Agent 成本的大头。一个复杂 Agent 的系统提示词动不动上万 token，20 轮会话就是 20 遍完整计算。缓存命中的部分只收十分之一的钱，而且实现方式几乎零成本，把不变的内容排到最前面就行，不用改架构。”

### 05、基于项目设计一个场景，如果遇到类似问题应该怎么解决？

“比如用户让 Agent 重构一个涉及 8 个文件的模块，改完后测试要全部通过。”

“先说为什么这个任务不能用 ReAct 单循环。ReAct 每轮做一件事——观察、思考、行动。它改了文件 A，中间跑一次测试，测试挂了。但这个’挂’不是因为 A 改错了，是因为 B、C、D 还没改。Agent 看到报错，可能会尝试修复一个根本不该修的问题，越改越乱。单循环没有全局视角，只看到当前这一步。”

【截图：ReAct vs Plan 模式对比；风格：data-board；截图目标：对比单循环和规划模式在多文件任务下的执行差异；关键词：ReAct、Plan、全局视角】

“这种任务要切到 Plan 模式。规划器先读完所有 8 个文件，理解模块内部的依赖关系，然后生成一个任务图。”

“任务图是一个 DAG（有向无环图）。假设 A 文件定义了接口，B 和 C 各自实现了这个接口，D 依赖 B 的输出。规划器生成的图大致是这样。先读所有文件（READ 类型，无依赖，并行）→ 改 A 的接口定义 → 改 B 和 C 的实现（互不依赖，并行）→ 改 D（依赖 B）→ 跑测试。执行按拓扑排序（Topological Sort）来，每一轮找出所有入度为 0 的节点——就是没有前置依赖的任务——这一批并行执行。这批完成后更新依赖图，再找下一批。”

【截图：DAG 任务图示例；风格：swimlane；截图目标：展示 8 个文件的依赖关系和拓扑排序执行顺序；关键词：DAG、拓扑排序、并行执行】

#### 改到一半发现计划有问题怎么办？

“比如改到第 4 个文件时发现，A 的接口变更还影响了一个之前漏掉的文件 E。”

“这时候分两种情况。如果进度不到一半，说明规划阶段对模块的理解可能有偏差，带着错误信息整体重新规划。如果进度过半，已完成的工作量太大，推倒重来不划算，保留已完成的部分，追加 E 的修改任务，调整后续依赖关系，接着执行。”

【截图：增量重规划决策逻辑；风格：swimlane；截图目标：展示进度过半和不过半时的不同处理策略；关键词：增量重规划、进度判断、依赖调整】

“如果任务还需要质量把关——比如重构后要确保 API 兼容性——切到 Team 模式。规划器拆任务，2 个 Worker 并行执行，审查器检查每批产出。审查器和 Worker 的职责严格隔离，审查器不碰工具，只做判断，避免自己改代码又自己审。不合格打回重做，最多 2 次。”

### 06、语义检索是如何实现的？

“派聪明用的是混合检索，向量检索和关键词检索结合。”

【截图：混合检索流程；风格：swimlane；截图目标：展示从 Query 到最终结果的完整检索流程；关键词：KNN、BM25、混合检索】

“先说向量检索。用户的查询文本通过 DashScope 的 text-embedding-v4 模型转成 2048 维的向量，然后在 Elasticsearch 里做 KNN 搜索。为了保证召回率，召回窗口设的比较大，是最终返回数量的 30 倍，如果最终要 5 条结果，KNN 先召回 150 条候选。”

“然后用 BM25 做二阶段重排序。在 KNN 召回的候选集上，对文本内容做关键词匹配打分。KNN 权重 0.2，BM25 权重 1.0，关键词匹配在排序中占主导。”

“这样做的好处是，向量检索负责语义层面的召回，不会漏掉表述不同但意思相近的内容；BM25 负责精排，确保关键词完全匹配的结果排在前面。”

#### 为什么用 BM25 做重排序？

【截图：向量检索 vs 混合检索效果对比；风格：data-board；截图目标：对比单独向量和混合检索的优劣；关键词：向量、BM25、召回率】

“向量检索有一个已知问题：对专有名词和缩写的匹配不够精确。用户搜‘MCP 协议’，向量可能会把‘RPC 协议’也召回来，因为语义上它们确实相近。但用户要的就是 MCP。BM25 能把关键词完全匹配的结果排到最前面，弥补向量检索在精确匹配上的不足。”

### 07、向量数据库在项目中具体承担什么作用？

“派聪明没有单独部署向量数据库，用 Elasticsearch 同时做向量存储和全文检索。”

“ES 里每条文档有两个核心字段。vector 字段存 2048 维的 Embedding 向量，ES 用 HNSW（Hierarchical Navigable Small World，分层可导航小世界图）算法建索引，做近似最近邻搜索。textContent 字段存原始文本，走 ES 自带的倒排索引做 BM25 关键词检索。一份数据、两套索引、两种检索能力。”

【截图：ES 双索引架构；风格：skill-card；截图目标：展示 vector 字段的 HNSW 索引和 textContent 字段的倒排索引如何共存；关键词：HNSW、倒排索引、双索引】

“文档入库前做分块，分块策略直接决定检索质量。分块大小 512 字符，相邻块重叠 100 字符。为什么要重叠？因为一个完整的概念可能正好跨在两个块的边界上，重叠保证边界处的语义不被截断。”

“分块逻辑分三级。先按双换行符切段落，每段独立。某段超过 512 字符，再按句子切分。切完如果某块不足 100 字符，就和前一块合并，太碎的块 Embedding 质量差，检索出来没什么用。”

【截图：文档分块和父子层级；风格：three-layer；截图目标：展示三级分块逻辑和父子文档结构；关键词：512 字符、重叠、父子块】

“文档还有一层父子结构。子块就是 512 字符的检索单元，用来做精确匹配。父块最大 1MB，差不多是整篇文档的全文。检索命中子块后，可以回溯到父块拿完整上下文，让 LLM 看到更多信息再回答。大文件用流式解析，防止一次加载撑爆内存。”

#### 什么情况下该换专门的向量数据库？

“看数据规模和检索 QPS。派聪明的知识库在几万到几十万文档这个量级，ES 的 HNSW 完全撑得住。多部署一个 Milvus 或者 Qdrant，要多维护一套集群、多做一份数据同步，收益不大。”

【截图：ES vs 专用向量数据库适用场景；风格：data-board；截图目标：对比不同数据规模下 ES 和专用向量数据库的优劣；关键词：数据规模、HNSW 内存、运维成本】

“但如果数据量到了千万级，或者检索 QPS 要求很高，ES 的 KNN 会成为瓶颈。HNSW 的内存开销随数据量线性增长，2048 维的向量每条占 8KB 左右，一千万条就是差不多 80GB 纯向量数据。到这个阶段，专用向量数据库的分布式检索和量化压缩能力就有价值了。”

### 08、langchain、langgraph 这些框架为什么选择？底层流程了解吗？

“PaiCLI 没有用任何 AI 框架，全部自研。HTTP 层用的 OkHttp 直连各家大模型的 API。”

【截图：自研 vs 框架的决策对比；风格：data-board；截图目标：对比自研和框架在不同维度的优劣；关键词：自研、框架、控制粒度】

“为什么不用框架？因为每家大模型的 API 规范不一样。GLM 的 Prompt Caching 用 glm-prompt-cache 模式，DeepSeek 用 automatic-prefix-cache，Kimi 用 moonshot-context-cache。错误码的定义、重试策略、流式输出的格式也各有差异。框架把这些差异抽象掉了，但我需要针对每家模型做精细控制，比如缓存命中率、token 计费、流式中断恢复，框架的抽象层反而挡路。”

LangGraph 的底层原理我了解。它围绕一个状态图（State Graph）展开，节点是处理函数，边是条件路由。每个节点接收当前状态、执行操作、返回更新后的状态。Checkpoint 机制把每步的状态快照存下来，支持断点恢复和回放。

#### 什么场景下你会选框架？

“如果是快速验证一个想法，用框架跑通原型比较快。但如果项目要上生产、要做多模型适配和精细化控制，自研更合适。现在 AI Coding 能力很强，自研的开发成本已经很低了。”

### 09、模型输出结果如何控制规则？

“三层，Prompt 约束、工具 Schema 校验、执行审批。”

“Prompt 层是软约束。系统提示词的第一层定义了行为边界，哪些操作可以做、哪些禁止、输出格式怎么组织。这些规则每轮对话都在，模型看得到。但 Prompt 毕竟是自然语言，模型不一定百分百遵守，特别是上下文很长、注意力分散的时候。所以需要后面两层硬约束兜底。”

“工具 Schema 层是硬约束。每个工具注册时带一个 JSON Schema，定义参数类型、必填项、取值范围。模型生成的工具调用参数必须通过 Schema 校验，不合规就拒绝执行，把错误消息返回给模型让它重新生成。比如 write_file 的 file_path 必须是字符串、content 不能为空——这些约束模型绕不过去。”

【截图：三层输出控制机制；风格：three-layer；截图目标：展示 Prompt（软约束）→ Schema（硬约束）→ 审批（人工兜底）的递进关系；关键词：Prompt、JSON Schema、HITL 审批】

“MCP 工具的 Schema 需要额外做一步清洗。MCP Server 返回的 Schema 经常带 $ref 引用和 anyOf 联合类型，模型遇到这些嵌套结构容易生成错误格式的参数。PaiCLI 在注册 MCP 工具时会把所有 $ref 展开、anyOf 拍平成最常用的类型，确保模型看到的是一个干净扁平的参数定义。”

【截图：MCP Schema 清洗前后对比；风格：data-board；截图目标：对比清洗前带 $ref/anyOf 的复杂 Schema 和清洗后的扁平 Schema；关键词：MCP、$ref、Schema 清洗】

“审批层管执行权限。即使参数完全合规，写操作在执行前还要过 HITL 审批。路径检查器拦截项目根目录以外的文件操作，命令检查器拦截危险命令。审批策略分三档，auto 自动通过、suggest 建议确认、never 必须手动确认，按工具的风险等级配置。”

#### 审批被用户拒绝后 Agent 怎么反应？

【截图：审批拒绝后的 Agent 决策流程；风格：swimlane；截图目标：展示工具调用被拒绝后模型的重新决策过程；关键词：拒绝、tool_result、重新决策】

“拒绝结果作为 tool_result 返回给模型，消息里写明'这个操作被用户拒绝了'。模型看到后自己决定下一步——可能换一种方式达成目标，比如用户拒绝了直接覆盖文件，模型改成先备份再写入。也可能告诉用户需要手动操作。Agent 不会因为一次拒绝卡死在那里。”

### 10、记忆模块是怎么设计的？

“三层记忆，各管各的。”

【截图：三层记忆架构；风格：three-layer；截图目标：展示短期、长期、项目三层记忆的存储和生命周期；关键词：短期记忆、长期记忆、项目记忆】

“短期记忆是会话级别的，只在当前会话内有效。底层是一个LinkedHashMap，先进来的排前面。token 预算是上下文窗口的 45%，超了就淘汰最旧的条目。”

“长期记忆是持久化的，跨会话存活。存在 SQLite 里，按类型和作用域分类。每轮 LLM 调用前，检索和当前输入相关的长期记忆条目，注入系统提示词。新存入的条目会做去重检测，避免重复。”

“项目记忆是开发者提前写好的规则文件，类似 Claude Code 的 CLAUDE.md。按优先级加载：PAI.md → .paicli/PAI.md → PAI.local.md → .paicli/PAI.local.md，后面的覆盖前面的。”

#### 派聪明的记忆设计有什么不同？

“派聪明的记忆更偏业务侧。”

【截图：派聪明记忆架构；风格：data-board；截图目标：对比 PaiCLI 和派聪明的记忆设计差异；关键词：Redis、MySQL、引用追踪】

“会话历史存 Redis，最近 20 条消息，7 天过期。同时持久化到 MySQL，保留完整的问答记录。每条回答还会记录引用映射——这条回答引用了哪个文档的哪个片段、检索分数多少、匹配了哪个关键词——用户点引用标记就能跳转到原文。”

“还有一个用户反馈记忆。用户对回答打好评或差评后，最近几条反馈会注入到下一轮的系统提示词里，引导模型调整回答风格。”

### 11、多轮、多会话场景下 memory 如何处理？

“多轮和多会话是两个不同的问题。”

“多轮场景，对话越来越长，上下文窗口迟早装不下。PaiCLI 的做法是保留最近 3 轮完整对话不动，更早的历史用 LLM 生成摘要替换。摘要保留关键诉求、已完成操作、达成的共识和待办事项。具体的压缩算法和触发阈值在第 13 题会细讲。”

“多轮场景还有一个容易忽略短期记忆的 token 预算管理。短期记忆存在一个LinkedHashMap里，预算上限是上下文窗口的 45%。超了就从最旧的条目开始淘汰。淘汰不是直接删除，被淘汰的条目先用 LLM 做一次压缩摘要再替换，关键信息不会完全丢掉。”

【截图：多轮多会话记忆处理流程；风格：swimlane；截图目标：展示多轮场景下短期记忆淘汰和多会话下长期记忆持久化的流转；关键词：短期记忆、长期记忆、会话隔离】

“多会话场景靠长期记忆的持久化。PaiCLI 的长期记忆存在 SQLite 里，按类型和作用域分类。新会话启动时从磁盘加载，Agent 还记得之前存过的偏好和规则。新存入的条目会做去重检测，同一条偏好不会存两份。”

“/clear 命令只清短期记忆和对话历史，长期记忆不受影响。用户说’清一下上下文’通常是想换个话题重新开始，不是想让 Agent 忘掉所有偏好。”

【截图：/clear 命令清除范围；风格：data-board；截图目标：对比 /clear 前后短期记忆、对话历史、长期记忆的状态变化；关键词：/clear、短期记忆、长期记忆】

“派聪明更简单。每个会话用独立的 conversation_id 隔离，同一个用户可以开多个会话互不干扰。会话历史存 Redis，最近 20 条消息，7 天过期，同时持久化到 MySQL。没有跨会话的长期记忆，但有一个用户反馈机制，最近几条好评差评注入系统提示词，影响后续回答的风格和侧重点。”

### 12、如果系统出现异常，整体的容错和异常处理机制怎么设计？

“分三层处理。”

【截图：容错机制分层架构；风格：three-layer；截图目标：展示 LLM 层、工具层、Agent 层的容错策略；关键词：重试、退避、降级】

“LLM 层，重试 3 次，指数退避加随机抖动。退避基数 500 毫秒，上限 30 秒。只有特定错误码才重试，比如 429（限流）、500/502/503/504（服务端异常）、408（超时）。400（参数错误）、401（认证失败）这些不重试，因为重试也不会好。如果响应头带了 Retry-After，优先用服务端建议的等待时间。”

“工具层，单个工具执行失败不中断整体流程。失败的工具返回一条错误消息，作为 tool_result 追加到对话历史，LLM 看到错误消息后自己决定是换一种方式重试还是跳过。并行执行的多个工具，总超时 90 秒。”

“Agent 层，防死循环。stagnation 检测到连续相同的工具调用就强制退出。Plan 模式下，如果任务执行到中途失败，看进度，进度不到一半就带着错误信息重新规划，进度过半就保留已完成的部分继续推进。”

#### 怎么判断是该重试还是该降级？

【截图：重试 vs 降级决策逻辑；风格：swimlane；截图目标：展示不同错误类型对应的处理策略；关键词：重试、降级、错误码】

“看错误的性质。暂时性错误（限流、网络抖动、服务端过载）重试，因为等一会儿大概率能恢复。持久性错误（认证失败、参数格式错误、SSL 异常）不重试，直接返回错误让上层处理。”

“重试 3 次都没成功，也就不再试了，返回错误消息。不做无限重试，用户在等着。”

### 13、再给一个上下文处理相关的场景题，如何优化 context 管理？

“比如一个 200K 窗口的 Agent，处理一个大型项目，对话到第 30 轮时上下文即将溢出。”

“先看 200K token 的空间怎么分。系统提示词占固定份额，9 层 Prompt 加上项目记忆和 Skills 索引，大约 1 到 2 万 token。短期记忆的预算是上下文窗口的 45%，差不多 90K。剩下的空间留给对话历史和 LLM 的生成输出。”

“到第 30 轮，对话历史加上工具调用的结果，token 数很可能已经逼近压缩触发阈值了。200K 窗口的触发阈值大约 167K，算法是窗口大小减去两个预留量，min(20K, 窗口/4) 预留给压缩后的摘要，min(13K, 窗口/8) 预留给后续对话。两个预留加起来大约 33K，200K 减掉就是 167K。预留空间的目的是防止压缩完马上又溢出。”

【截图：200K 窗口 token 分配和压缩触发；风格：data-board；截图目标：展示各部分的 token 占比和 167K 触发阈值的计算过程；关键词：200K、167K、token 分配】

“触发压缩后分三步。第一步扫描对话历史，找到所有 user 消息的位置索引。第二步从最后一条 user 消息往前数 3 条，这 3 轮完整对话标记为保留区，保留区内的所有消息，包括 user、assistant、tool_call、tool_result，都不动。第三步把保留区之前的所有消息发给 LLM 生成摘要，摘要替换掉原始消息。”

“摘要必须保留四类信息，用户的关键诉求、已完成的操作、双方达成的共识、待办事项。丢了任何一类都可能导致后续行为出错。比如摘要没记录用户说过'不要动 config 目录'，压缩后 Agent 可能就去改 config 了。”

#### 分割点为什么必须在 user 消息边界？

“tool_call 和 tool_result 是成对出现的。tool_call 是模型发起的工具调用请求，tool_result 是工具执行后返回的结果。如果从中间切断，会出现两种残缺状态。模型看到一个没有结果的工具调用，会以为工具还在执行；或者看到一个没有请求的工具结果，不知道这个结果是怎么来的。两种情况都会让后续推理跑偏。”

【截图：安全分割点 vs 危险分割点对比；风格：swimlane；截图目标：展示在 user 边界切分和在 tool_call/result 中间切分的后果差异；关键词：分割点、user 边界、tool_call 对】

“user 消息是天然的安全切分点。每轮对话以 user 消息开始，它前面的 tool_call 和 tool_result 一定是成对完整的。从这里切，不会破坏任何工具交互的完整性。”

“如果压缩一次还不够——大型项目里摘要本身也可能好几千 token——可以手动触发强制压缩，保留轮数从 3 降到 1，只留最近一轮完整对话。代价是丢失更多上下文细节，但总比窗口溢出导致 Agent 直接报错要好。”
