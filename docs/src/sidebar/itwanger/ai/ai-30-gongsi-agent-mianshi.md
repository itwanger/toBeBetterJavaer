AI行业看起来热闹，但真正值得长期关注的公司，其实就那么几家。

我综合考虑了技术含金量、岗位数量、业务落地、成长空间和履历价值，整理了目前最值得去冲的 30 家公司。

### 01、系统如何区分正常重试和无效循环？「有没有取得进展」用什么指标判断？

「我在 PaiCLI 里做了一套工具签名的滑动窗口机制来检测循环。」

每一轮 Agent 调用完工具之后，系统会把这一轮的工具调用生成一个签名，签名由工具名加上参数拼接而成。

然后用一个固定大小的滑动窗口，把每轮的新签名放进来。如果窗口里的 3 个签名完全一样，就判定为无效循环。

![](https://cdn.paicoding.com/stutymore/ai-30-gongsi-agent-mianshi-20260818102118-618f1a2d.png)

举个例子，Agent 连续三次调用 grep_code，但每次搜的关键词都不一样，说明它在尝试不同的检索策略。只有工具名和参数都完全一样的时候，才说明 Agent 卡住了。

#### 为什么用工具签名而不是对比 LLM 输出文本来判断循环？

LLM 每次生成的文本都有随机性，即使在做完全重复的事情，输出也会有差异。

![](https://cdn.paicoding.com/stutymore/ai-30-gongsi-agent-mianshi-20260818102242-607763c8.png)

工具调用是结构化的，工具名和参数是精确的字符串，要么完全一样，要么不一样。判断起来简单可靠。

### 02、Agent 达到最大执行轮数但只完成部分工作，是直接退出还是返回部分结果？

在交互场景下，我会默认不限制固定轮数，让 Agent 根据任务是否完成自然结束，同时通过上下文压缩、重复调用检测和用户取消来保证安全。对于后台任务这类无人值守场景，可以显式设置最大轮数。

如果真的达到上限，Agent 会立即停止调用工具，再进行一次无工具的收尾，让模型根据已有工具结果返回部分成果，明确说明哪些已经完成、哪些已经验证、哪些还没完成、阻塞原因和下一步建议。

这样既不会因为达到上限就丢掉前面的工作，也不会让 Agent 为了收尾继续无限调用工具。

### 03、项目中哪些是自己开发的？哪些复用现成的框架？

「PaiCLI 没有用任何 AI 框架，全部由 Codex + Claude Code 完成。」

包括：ReAct、工具调度、Prompt 组装、上下文压缩、记忆系统、多 Agent 编排、Skill 体系等。MCP 客户端也是自己实现的，包括 JSON-RPC 协议层和传输层，stdio 和 Streamable HTTP 都支持。

![](https://cdn.paicoding.com/stutymore/ai-30-gongsi-agent-mianshi-20260818102635-a9b88883.png)

至于第三方类库，主要用 OkHttp 做 HTTP 请求，Jackson 做 JSON 序列化，SQLite 做持久化存储，JavaParser 做代码 AST 解析，JGit 做 Git 操作，Lanterna 做终端 TUI 渲染，Jieba 做中文分词。

### 04、多 Agent 协同执行时可能遇到哪些性能瓶颈？如何解决？

「最大的瓶颈是 LLM 的 API 调用延迟。」

多 Agent 编排里每个 Worker 每一轮都要调一次 LLM，多个 Worker 并行跑下来，LLM 调用次数会很多。

解决思路是让没有依赖关系的任务尽量并行。PaiCLI 把规划器生成的执行计划解析成 DAG，按拓扑排序分批调度，同一批内的任务可以并行执行。

![](https://cdn.paicoding.com/stutymore/ai-30-gongsi-agent-mianshi-20260818103022-060c4724.png)

第二个瓶颈是共享资源的竞争。对话历史是隔离的，每个 Worker 有自己的消息列表，但工具注册表和记忆管理是共享的，多个 Worker 同时读写就会产生竞争。

PaiCLI 的做法是规划器和审查器只做判断，不执行工具调用，工具执行权集中在 Worker 手里。

### 05、如何控制 Agent 并发数量？有哪些限流或调度策略？

「多 Agent 编排模式用 BlockingQueue 做 Worker 池化。」

系统默认创建 2 个 Worker，线程池大小也是 2。每批可并行执行的任务数取决于当前空闲的 Worker 数量。

Worker 执行完一个步骤后自动归还到队列里，下一个步骤可以立即领走。

![](https://cdn.paicoding.com/stutymore/ai-30-gongsi-agent-mianshi-20260818103225-5df84de6.png)

后台任务队列用的是 FIFO 轮询机制。Worker 数量通过配置项控制，默认 2 个，每个 Worker 以 300 毫秒为间隔轮询 SQLite 数据库，取出状态为待执行的任务来跑。

### 06、直播场景大量用户同时点赞，如何优化？

客户端先做聚合，用户点了多少次先在本地存，存一批后再发给服务端。

![](https://cdn.paicoding.com/stutymore/ai-30-gongsi-agent-mianshi-20260818103904-8e36a893.png)

服务端收到请求后用 Redis 的 INCRBY 做原子累加，不走数据库。然后用定时任务把 Redis 里的计数批量刷回数据库。

### 07、目前 RAG 最大的瓶颈是什么？

「检索质量。」

检索阶段召回的文档如果和用户问题不相关，大模型拿着一堆无关内容去生成回答，质量就会很差。

![](https://cdn.paicoding.com/stutymore/ai-30-gongsi-agent-mianshi-20260818104220-8673ea05.png)

分块粒度最影响召回的质量。分块太大噪音就多，太小容易语义断裂。拿派聪明的经验来说，512 字符加 100 个字符重叠是一个比较稳妥的经验值。

### 08、给电商平台搭建百万级商品知识库问答系统，怎么设计？

商品信息里标题、描述、参数表、用户评价的切分策略不能一样。标题和参数表按字段切，描述和评价按语义切。

![](https://cdn.paicoding.com/stutymore/ai-30-gongsi-agent-mianshi-20260818104600-435011f7.png)

Embedding 用的阿里的 text-embedding-v4。检索层用混合检索，ES 先做 KNN 向量召回，再在候选集上做 BM25 关键词重排序。

「电商场景里用户经常搜具体型号和参数，关键词匹配比语义相似度更准，所以 BM25 权重要比向量高。」

![](https://cdn.paicoding.com/stutymore/ai-30-gongsi-agent-mianshi-20260818104803-c5ebfa77.png)

生成层用 DeepSeek V4，temperature 偏低，检索结果注入 Prompt 强制模型基于检索内容回答。

### 09、商品信息动态更新，知识库设计需要考虑什么？

核心思路是增量更新。每次商品信息变更时算一个 MD5 指纹，和上一次入库的指纹比，一样就跳过，不一样才对变更部分重新分块、重新生成 Embedding。

![](https://cdn.paicoding.com/stutymore/ai-30-gongsi-agent-mianshi-20260818110639-16a7eb42.png)

版本管理也要做。每个 chunk 带版本字段，更新时新版本入库，旧版本打标记但不立即删。查询只命中最新版本。

#### 为什么不直接删旧版本？

「ES 的删除是异步的，删除和查询并发执行可能出现短暂的数据空白。」

商家后台改商品信息时发 Webhook 做实时增量更新，同时跑一个定时任务全量扫描兜底，防止 Webhook 漏消息。

### 10、测试说你的接口有问题，你会怎么做？如何排查？

「先复现。」

找测试同学问清楚入参、请求环境、操作步骤和返回结果。拿到这些信息之后自己跑一遍，看能不能复现。

能复现的 bug 就已经解决了一半。

如果能复现，直接看日志。先定位到请求对应的日志行，看有没有异常堆栈。

有堆栈的话，顺着堆栈找到出问题的代码位置，分析入参在那个位置为什么会触发异常。

![](https://cdn.paicoding.com/stutymore/ai-30-gongsi-agent-mianshi-20260818111223-259344d8.png)

如果日志里没有异常，说明代码没报错但返回了不对的数据。这种情况需要回溯一下数据的流向，从入口开始，看每一步数据经过了哪些处理，在哪一步变成了不符合预期的样子。

复现不了时先排除环境差异。有些 bug 只在特定数据组合下才会触发。修完之后补一个回归测试用例，把这次的入参和预期结果固化下来。
